# 第 04 章：工具设计与可靠交付

## 本章目标

1. 会写"模型能正确使用"的工具（不是能跑的 Python 函数就行）
2. 用**结构化输出**替掉你 `re.search` / `JSON.parse` 的旧习惯
3. 分清两种结构化输出的用法：模型级 vs agent 级

**配套例子**：`examples/07_structured_output.py`

---

## 概念：工具是给模型看的接口文档

`@tool` 装饰的普通函数，对模型来说就是一份 **OpenAPI 文档**。你已经写过无数接口文档，所以直接看映射：

| 写接口时的考虑 | 工具里的对应物 | 影响 |
|---|---|---|
| 接口名要见名知意 | 函数名 `get_weather` | 模型靠它选工具 |
| 参数要有描述 | **docstring 里的参数说明** | 模型靠它抽参数 |
| 参数要限定类型/枚举 | **类型标注 + `Literal` / Pydantic** | 减少格式错误 |
| 错误要返回结构化错误码 | 返回 `"错误：..."` 而不是抛异常 | 让模型能自己纠偏 |
| 危险接口要权限 | 高危操作走人工审批（第 07 章） | 安全边界 |

**反着理解一遍：你写接口时最烦"参数含义不明的 SDK"，模型对工具的感受完全一样。**

## 跟着做（第一部分）：结构化输出

```bash
cd examples
uv run python 07_structured_output.py
```

核心就三行：

```python
class OrderIntent(BaseModel):
    product: str = Field(description="商品名，例如 拿铁")
    quantity: int = Field(description="数量，至少 1", ge=1)
    size: Literal["中杯", "大杯", "超大杯"] = Field(description="杯型")
    ...

agent = create_agent(
    model=get_model(),
    tools=[],
    response_format=ToolStrategy(OrderIntent),      # ★ 声明你要的 schema
)

result = agent.invoke({"messages": [{"role": "user", "content": "帮我点两杯大杯拿铁，要开发票，少冰。"}]})
order: OrderIntent = result["structured_response"]   # ★ 直接就是对象，不是字符串
```

三个必须记住的点：

1. **结果不在 `messages` 里**，在 `result["structured_response"]`。这是新手最常踩的坑（一直打印最后一条消息，然后说"没有结构化输出"）。
2. **`Literal` 就是枚举**。你写 TypeScript 的 `'中杯' | '大杯'` 怎么写，这里就怎么写。模型会自己对齐取值。
3. **拿到对象之后是普通 Python**。示例里 `order.quantity * 28` 直接算钱——这一步再也不用担心"两杯"还是"2 杯"。

---

## 概念：为什么必须这么做（这是本章的中心思想）

对比两种写法：

```
❌ 旧习惯
text = model.invoke("用户想点几杯？").content
m = re.search(r"(\d+)杯", text)      # 模型说"双份"→ 匹配不到 → 崩
                                     # 模型说"两杯"→ 崩
                                     # 模型加了"不加糖"→ 你可能抽错

✅ 正确做法
声明 schema → 模型自己对齐字段 → 校验失败时按策略重试 → 你拿到的是对象
```

**本质区别**：正则是在"猜自然语言的规律"，结构化输出是"把对齐责任交给模型，并且由 schema 做最后校验"。后者有两个额外好处：schema 本身就是**给模型的说明书**，同时也是**给你自己的数据契约**（写进文档、写进测试）。

---

## 概念：两种结构化输出，别混用

你会在两个层次上遇到它，用途不同：

| | 模型级 | agent 级 |
|---|---|---|
| 写法 | `model.with_structured_output(Schema)` | `create_agent(..., response_format=ToolStrategy(Schema))` |
| 适合 | 单步抽取/分类，不需要工具 | 需要先调工具、再给结构化结论 |
| 例子 | `12_mini_project_coffee_shop.py` 的 `classify` 节点 | `07_structured_output.py` |
| 何时选 | **默认用这个**，简单直接 | 结论依赖工具返回的数据时 |

示例 `12` 里的分类节点用的就是模型级写法，因为"把一句话分类"不需要工具：

```python
intent = get_model(temperature=0).with_structured_output(Intent).invoke(
    f"判断下面这句话的意图：{state['message']}"
)
```

**判断标准一句话：这个结构化结果需不需要"先查点东西"？需要 → agent 级；不需要 → 模型级。**

---

## 概念：策略与版本细节

`response_format` 接收的是**策略对象**，最常见的是 `ToolStrategy`。官方的规则是：

- 不指定策略时，`langchain>=1.1` 会**按模型 profile 自动选择**（Provider 原生结构化输出 / Tool 调用模拟）
- `ToolStrategy` 的 `handle_errors` 可以控制**校验失败后是否自动把错误回灌给模型重试**——这正是"可靠交付"的关键旋钮
- `ProviderStrategy` 的 `strict` 参数有版本要求（`>=1.2`）

**不确定你装的版本支持哪个参数时，别猜**——用第 00 章 `00_env_check.py` 那种方式现场验证（第 14 章有现成命令）。

## 跟着做（第二部分）：写一个"好用"的工具

给第 02 章的 agent 加一个工具，刻意按下面的标准写，然后对比"随便写"的版本：

```python
@tool
def lookup_order(phone: str) -> str:
    """根据手机号查询最近的订单。

    Args:
        phone: 11 位中国大陆手机号，例如 13800000000。不要传姓名或昵称。

    Returns:
        一行文本，格式为"最近一笔订单：<商品> ×<数量>，金额 <金额> 元，状态 <状态>"。
        查不到时返回"未找到订单"。
    """
    ...
```

三个刻意的设计：

1. **参数说明里写了反例**（"不要传姓名或昵称"）——这是在替模型排除错误选项，比事后调试便宜得多。
2. **返回格式写清楚了**——模型知道拿到的是什么形状，后续推理更稳。
3. **查不到时返回固定文案**，不是抛异常——模型能说出"没查到"，而不是死在异常里。

## 自己动手改

1. **把 schema 写严一点**：给 `OrderIntent` 加 `note: str = Field(default="")`，再问一句"少冰、多加一份糖浆"（两个备注），看模型怎么塞。
2. **故意让 schema 不满足**：把 `quantity` 设成 `ge=1`，然后输入"帮我点 0 杯咖啡"。观察它是报错、还是自动纠正为 1。**这一条能让你理解 `handle_errors` 的价值。**
3. **制造工具描述歧义**：把 `lookup_order` 的 docstring 改成 `"查询订单"`，重跑，看参数抽取质量有没有下降。改回来再对比。
4. **把 `Literal` 换成 `str`**，看模型会不会给出"中杯/大杯"之外的值（比如"超小杯"）。这就是"用类型约束代替提示词约束"。

## 坑

- **打印错地方**：`structured_response` 不在 `messages` 里。
- **schema 写太松**：全是 `str`，等于没约束。该用 `Literal` 用 `Literal`，该用 `ge=`/`le=` 用。
- **在中文里混用 ASCII 引号**：`print("……"起草"……")` 在 Python 里是语法错误。写中文注释和字符串时特别注意（这是我在写示例时真踩过的坑）。
- **把 `bind_tools` 过的模型传给 `create_agent`**：v1 不支持预绑工具（第 03 章提过）。
- **`create_agent` 不支持 Pydantic 状态 schema**：结构化输出用的是 `response_format`，别和"状态定义"混为一谈。
