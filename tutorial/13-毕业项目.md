# 第 13 章：毕业项目——用 LangGraph 重写一条真实链路

## 本章目标

1. 拿一个**真实存在、且已经暴露过问题**的案例当需求，用你学到的东西重写
2. 一次解决三类典型毛病：脆弱判定、无持久化、假成功
3. 拿到一份可以放进 GitHub 的仓库（有评测、有测试、有 README）

## 概念：为什么拿这个案例当毕业项目

仓库里的 `../virtual_rnd_center/` 是一条完整的研发自动化链路：

```
需求访谈 → 需求文档 → 架构 + 代码 → 代码审查 → 部署 → 接口测试 → 裁决 →（不过）重工
```

它是用另一个框架写的，但**你要的不是它的代码，是它的需求**。它有三个已经被我核实过的真实缺陷（都在代码里）：

| # | 原始做法 | 为什么错 | 你该怎么改 |
|---|---|---|---|
| 1 | 扫 Markdown 报告里有没有 `APPROVED` / `REJECTED` 字样判定通过 | 报告里只要**提到**这个词就误判；换个措辞就失准 | `response_format` + Pydantic `Verdict` |
| 2 | 没有任何持久化，跑一半崩了从头来 | 长链路重跑成本极高（每一步都过模型） | `compile(checkpointer=SqliteSaver(...))` + `thread_id` |
| 3 | 部署失败时返回伪造的 `RUNNING (healthy)` | 流水线会撒谎，下游全错 | 显式失败，交条件边处理 |

**这三条正是"智能体工程"和"智能体演示"的分界线。**修掉它们，你的水平就跨过一个台阶。

还有一条它**做对了**、你要保留的设计：**重工时跳过昂贵的前期（不重跑需求访谈），只重跑"代码 → 审查 → 部署 → 测试"**。这是真正的工程直觉，照抄。

## 概念：先定状态，再画图，最后写节点

**顺序不能反。**新手最常见的错误是先写节点函数，写到一半发现状态里缺字段。

### 状态草案

```python
from typing import Annotated
from typing_extensions import TypedDict
from operator import add
from pydantic import BaseModel, Field


class Verdict(BaseModel):
    """一次评审的结构化结论。"""
    passed: bool = Field(description="是否通过")
    reasons: list[str] = Field(description="不通过的具体原因；通过则为空列表")


class RndState(TypedDict):
    requirement: str                      # 原始需求
    boundary: str                         # 边界清单（文件路径或文本）
    verdicts: Annotated[list[str], add]   # 每轮结论，追加（★ 必须带 reducer）
    round: int                            # 当前第几轮
    max_rounds: int                       # 硬上限
    artifact_dir: str                     # 产物目录（状态里只放路径，不放内容）
```

**两个刻意的设计**：

- `verdicts` 用 `add` reducer：它要跨轮累积。**忘了 reducer，你只能看到最后一轮**（第 05 章的坑）。
- 状态里只放**路径**，不放文件内容：状态每轮都会落盘，塞大文本会让 checkpoint 爆炸（第 06 章）。

### 节点清单（9 个）

```
START → interview → write_boundary → write_requirements → generate_code
      → code_review → deploy → qa_test → gate ─┬─ rework →（回到 generate_code）
                                               └─ finalize → END
```

| 节点 | 干什么 | 对应原案例哪个任务 |
|---|---|---|
| `interview` | `interrupt()` 问人类几个二元问题 | 需求访谈（**带 `human_input` 的那个**） |
| `write_boundary` | 落盘边界清单 | 边界澄清 |
| `write_requirements` | 落盘需求文档 | BA 的需求文档 |
| `generate_code` | 生成代码到 `artifact_dir` | 架构 + 开发 |
| `code_review` | 结构化评审 → `Verdict` | 代码审查 |
| `deploy` | 部署（**失败必须显式失败**） | 部署 |
| `qa_test` | 接口测试 | 接口测试 |
| `gate` | 条件边：通过 → `finalize`；不过且 `round < max_rounds` → `rework`；超限 → `interrupt()` 问人 | 裁决 / 路由 |
| `rework` | `round += 1`，回 `generate_code` | 重工 |

**`gate` 是这一章的核心**：它把"关键词扫描"换成"结构化判定 + 显式业务规则"，并且把**超限处理交给人**，而不是硬闯或死循环。

## 跟着做：按里程碑推进（别想一次写完）

### 里程碑 1：跑通骨架（先不要模型）

**目标**：图能编译、能跑完一轮、能中断、能恢复。**节点里先用假数据。**

```python
def code_review(state: RndState) -> dict:
    verdict = Verdict(passed=True, reasons=[])          # ← 先写死
    return {"verdicts": [verdict.model_dump_json()]}
```

**为什么先假后真？** 因为"流程正确"和"模型正确"是两类问题。混在一起调，你分不清错在哪层（第 01 章的分层思想在这里救了你的时间）。

### 里程碑 2：换持久化，验证断点续跑

```python
from langgraph.checkpoint.sqlite import SqliteSaver

with SqliteSaver.from_conn_string("rnd.db") as cp:
    graph = build_graph().compile(checkpointer=cp)
    config = {"configurable": {"thread_id": "proj-001"}}
```

**验证方式**：跑到一半 `Ctrl+C`，重新运行同一个 `thread_id`，确认它能接着跑（第 06 章那个"杀进程"实验，这次用在你自己的项目上）。

### 里程碑 3：把生成与判定都换成模型 + 结构化输出

```python
# 判定（替代扫关键词）
agent = create_agent(
    model=get_model(temperature=0.15),        # ★ 审计用低温
    tools=[],
    system_prompt="你是严格的代码审查员。只根据给定的代码与需求判定，不要臆测。",
    response_format=ToolStrategy(Verdict),    # ★ 结构化交付，禁止自由文本判定
)
verdict = result["structured_response"]
return {"verdicts": [verdict.model_dump_json()]}
```

**同时给不同节点不同的温度**（这是原案例分享稿里做对的一件事）：

| 角色 | 温度 | 理由 |
|---|---|---|
| 需求 / 代码生成 | 0.8 左右 | 需要发散 |
| 审查 / 裁决 | 0.1–0.2 | 需要稳定 |
| 运维类操作 | 0 左右 | 只需要确定性 |

### 里程碑 4：加知识库节点（进阶）

把**历史评审意见**和**编码规范**灌进向量库；重工时检索"上次为什么被拒"，作为上下文塞给生成节点。

要点（第 08、09 章的知识）：

- 灌数据是**独立的、可重跑的脚本**（`scripts/index_rules.py`），不是 agent 运行的一部分
- 用**稳定 id**（文件路径 + 行号 / hash），别用随机 uuid
- 检索结果**带上来源 metadata**，写进上下文，让人能核对

**这一条的价值**：它把"重工"从"重来一遍"变成"带着上次的教训重来"。**这是原案例完全没做到的。**

### 里程碑 5：评测与测试

```python
CASES = [
    # 固定需求 → 断言
    ("做一个待办事项 App", lambda final: final["round"] <= 3 and Path(final["artifact_dir"]).exists()),
    ("做一个天气查询服务", lambda final: ...),
    ("做一个留言板", lambda final: ...),
]
```

**三个必须断言的**：

1. 产物真的存在（文件、目录）
2. 最终通过（或明确失败，而不是"假装成功"）
3. **轮数 ≤ `max_rounds`**（防止无限重工）

## 概念：九条硬要求（验收清单）

| # | 要求 | 对应你学的 |
|---|---|---|
| 1 | 三方判定（审查/部署/测试）全部结构化输出，**禁止正则扫报告** | 第 04 章 |
| 2 | `SqliteSaver` 持久化，`Ctrl+C` 后同 `thread_id` 能继续 | 第 06 章 |
| 3 | `max_rounds` 超限 → `interrupt()` **转人工** | 第 07 章 |
| 4 | 重工**跳过需求访谈**，只重跑 代码→审查→部署→测试 | 第 05 章（条件边） |
| 5 | 工具/部署失败**显式失败**，不许伪造成功 | 第 11 章（安全） |
| 6 | **加知识库节点**：历史评审意见 + 编码规范，可重跑灌数据 | 第 08、09 章 |
| 7 | **记录检索质量**：相似度 / MMR / 元数据过滤 三档对比 | 第 09 章 |
| 8 | **接一个 MCP 工具**（可先用官方文档 server 练手） | 第 10 章 |
| 9 | **评测脚本**：3 条固定需求 × 断言 | 第 11 章 |

**第 6–8 条是可以降级为"可选"的**（如果你时间紧）。但**第 1、2、3、5、9 不能砍**——它们正好对应原案例的三个毛病 + 一个必然事故 + 无法维护。

## 看懂结果

跑完之后，回答这六个问题（第 12 章的"六问审阅法"，用在你自己身上）：

| 问题 | 你的答案应该是 |
|---|---|
| 每个节点被喂了什么上下文？ | 只说得出"路径 + 检索到的历史教训" |
| 它凭什么判断自己干完了？ | `Verdict` 结构化 + 条件边 |
| 失败了谁纠偏？ | 重工回边；超限转人工 |
| 副作用在哪执行？ | 在 `interrupt()` 之后 / 只在 `finalize` |
| 权限边界靠什么？ | 代码（路径约束）+ 审批 |
| 改一版怎么知道没变差？ | `eval.py` 通过率 |

**六问全答得出来，你就毕业了。**不是"读完了教程"，是"能做对一件事"。

## 自己动手改（毕业之后）

1. **加一个"设计评审"节点**，放在 `write_requirements` 之后、`generate_code` 之前。**练手：给图插节点、改边、给状态加字段。**
2. **把 `SqliteSaver` 换成 `PostgresSaver`**，让它能跑在服务器上。
3. **做一个"审批人"界面**：第 11 章的前端部分——展示中断载荷（模型草案 + 风险点），三个按钮（批准/编辑/拒绝）。**这是你前端背景的用武之地。**
4. **加时间旅行调试**：用 `get_state_history` 找到"第 2 轮重工那次"，看当时它看到的上下文是什么、为什么判定不通过。**这是排查长链路唯一的有效手段。**
5. **给重工加"增量保护"**：重工时只删报告、不删已生成的源码（原案例这点做对了，你抄过来）。
6. **做完附录 F 的精读**：把偏差清单里「值得学」的条目真正抄进这个项目——生产代码是你毕业之后的第二需求来源。

## 坑

- **先写节点再定状态**：写到一半发现缺字段，全部返工。
- **一次把模型接进去**：流程 bug 和模型 bug 混在一起，无法定位（用里程碑 1 的假数据隔离）。
- **忘了给状态里的累积字段挂 reducer**：跨轮信息静默丢失。
- **`max_rounds` 只在 prompt 里说**：模型不会遵守，必须在条件边里判断。
- **重工时不删旧报告**：目录里堆着多轮产物，模型会看到互相矛盾的内容。
- **把灌数据写成 agent 启动流程的一部分**：每次启动都重新 embedding。
- **没有评测就宣布完成**：那你交付的是"感觉能跑"。
