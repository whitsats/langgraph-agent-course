# 第 03 章：手写智能体循环 ★

> **这是整个教程最重要的一章。** 如果你只做一件事，做这件。

## 本章目标

1. 用 50 行把 `create_agent` 内部做的事手工走一遍
2. 亲手实现循环必须自己负责的**五件事**（框架替你兜的就是这些）
3. 从此看任何框架文档，你都知道"它在补我手写版的哪个坑"

**配套例子**：`examples/03_handwritten_loop.py`

---

## 概念：循环只有四步，但每一步都有坑

```
① 把消息列表发给模型
② 模型要是说"我要调工具" → 执行工具，把结果塞回消息列表 → 回 ①
③ 模型要是没要工具 → 它的回答就是最终答案，结束
④ 但如果它一直要工具呢？→ 你必须自己设上限
```

第 ④ 步是分水岭。**没有任何教程告诉你"如果没有第 ④ 步会怎样"，因为那要等着线上卡死你才知道。**手写一遍，你就永远记得。

---

## 跟着做

```bash
cd examples
uv run python 03_handwritten_loop.py
```

看输出，你会看到每次循环的过程：

```
--- 第 1 轮：把 1 条消息发给模型 ---
    模型要求调用: get_weather({'city': '上海'})
    工具返回: 多云 26 度

--- 第 2 轮：把 3 条消息发给模型 ---
    模型要求调用: calculate({'expression': '26 + 3'})
    工具返回: 29

--- 第 3 轮：把 5 条消息发给模型 ---
--- 模型不再需要工具，循环结束 ---
```

注意每一轮的**消息条数在涨**：1 → 3 → 5。这就是"上下文在累积"的物理过程。**每涨一轮，下一次请求的 token 就更多、更慢、更贵。**长任务最后崩掉，根源都在这。第 11 章讲的"上下文工程"，就是专门处理这件事。

---

## 概念：循环必须自己负责的五件事

对着 `03_handwritten_loop.py` 一条条看，这就是框架真正的价值清单：

| # | 要负责的事 | 手写版怎么做的 | 框架版谁负责 |
|---|---|---|---|
| 1 | **工具 schema 生成** | `model.bind_tools(...)` | `create_agent` 自动 |
| 2 | **工具分发与异常兜底** | `TOOLS.get(name)` + `try/except` | 内置 + 可配中间件 |
| 3 | **终止判定** | 没有 `tool_calls` 就停 | 内置 |
| 4 | **步数上限** | `MAX_STEPS = 6` | `recursion_limit`（**有默认值，超了会抛错**） |
| 5 | **上下文裁剪** | ❌ 手写版没做 | 摘要/裁剪类中间件 |

第 5 条是手写版故意留白的地方——**你跑长任务时它必然爆**，而框架有现成方案。体会到这层落差，你才会明白为什么要用框架，而不是"因为别人都在用"。

---

## 概念：三个必须记住的细节

### 1. `bind_tools` 是"告诉模型有哪些工具"

```python
model_with_tools = model.bind_tools(list(TOOLS.values()))
ai = model_with_tools.invoke(messages)
```

模型随后可能返回 `ai.tool_calls`，形如：

```python
[{"name": "get_weather", "args": {"city": "上海"}, "id": "call_abc123"}]
```

**注意那个 `id`**——回灌结果时必须带上它，见下一条。

### 2. 工具结果必须用 `ToolMessage` 且带 `tool_call_id`

```python
messages.append(ToolMessage(content=str(output), tool_call_id=call_id))
```

`tool_call_id` 是模型用来**配对**"我第几次请求的结果回来了"的。漏了它，多工具场景会错位；写成普通 dict（`{"role": "tool", ...}`）在某些模型上能跑、在另一些上直接报错。

> ⚠️ **v1 有个坑**：不要把你手工 `bind_tools` 出来的模型再传给 `create_agent`。v1 明确不再支持"预绑工具"的模型实例，会报错或行为异常。要么让 `create_agent` 自己绑，要么就纯手写。

### 3. 工具失败要**显式返回给模型**，不要抛出去

```python
try:
    output = tool_fn.invoke(args)
except Exception as e:
    output = f"工具执行失败：{type(e).__name__}: {e}"
```

这条是**设计抉择**，不是习惯：把错误当"观察结果"喂回模型，它有机会自己换参数、换工具、或者坦白说做不到。直接抛异常，流程就死了。

**但注意**：涉及钱、删除、发布这类操作，失败就该真的失败（第 11 章讲"禁止假成功"）。区分标准是：**这个失败，模型有可能自己救回来吗？**能——喂回去；不能——中断并报警。

## 看懂输出

最后那段"和框架对比"是本例的正文，虽然看着像彩蛋：

```
  手写这份代码里，下面这些都要你自己负责：
   - 消息列表怎么累积、工具结果怎么回灌
   - 工具不存在 / 抛异常怎么办
   - 什么时候停（不再要工具 / 步数上限 / 循环检测）
   - 上下文太长怎么裁剪
```

对照第 02 章的例子：`create_agent` 那 15 行，把这些全替你做了。**现在你再回去看那 15 行，看到的东西和昨天完全不一样**——这就是为什么顺序必须是"先手写，再看框架"。

## 自己动手改（每一改都是"制造一类故障"）

1. **删掉 `MAX_STEPS` 上限**（把 `range(1, MAX_STEPS + 1)` 改成 `while True`），问一个它答不出来的问题（比如"帮我查一下火星天气"）。观察它会不会反复调工具、一直转。**这就是线上卡死的原型。**
2. **删掉 `try/except`**（或者让工具故意抛异常），看报错长什么样。再决定：这个错该喂回模型还是该中断？
3. **删掉 `tool_call_id`**，看会不会报错、或者多工具时结果错位。
4. **给工具加错误返回**：让 `get_weather` 对未知城市返回 `"错误：不支持该城市"`，看模型接下来会不会自己换城市、还是直接编一个答案。

## 验收问题

1. 循环的终止条件有哪几种？为什么**步数上限是必须的**？
2. 为什么工具异常要喂回模型而不是抛出？有没有反例？
3. `tool_call_id` 不传会怎样？
4. 手写版故意没做上下文裁剪，会导致什么？（提示：看每一轮消息条数）
5. 说清 `bind_tools` 和 `create_agent(tools=...)` 的关系，以及为什么不能把两者混用。

## 坑

- **`while True` 没有上限**：本地跑可能只是卡住，线上是烧钱 + 服务不可用。LangGraph 那边对应的报错是 `GRAPH_RECURSION_LIMIT`（详见第 14 章排错表）。
- **把工具结果拼成普通字符串塞进 user 消息**："工具说：多云 26 度"这种写法模型能读，但多工具时会分不清哪条是谁的，也会破坏缓存。用 `ToolMessage`。
- **`args` 直接当成可信输入**：`args` 是**模型生成的**，等于外部输入。示例里 `calculate` 用字符白名单而不是裸 `eval`，就是在演示这条。生产里路径、SQL、shell 参数一律要白名单或沙箱。
- **以为模型会自己检测循环**。不会。它每轮都"很合理地"再调一次工具。
