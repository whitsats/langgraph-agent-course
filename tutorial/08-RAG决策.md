# 第 08 章：RAG——先决定要不要知识库

## 本章目标

1. 学会**五问决策法**：这一半的功夫能省下你一半的无用功
2. 认清 RAG 不是一条流水线，而是**"给 agent 接一个检索工具"**
3. 亲手做出一个"知识库里没有就说不知道"的 agent，并知道怎么测它

**配套例子**：`examples/09_rag_agent.py`（需要 Key）、`examples/04_index_offline.py`（离线）

---

## 概念：先别写代码，先回答五个问题

绝大多数"我该上 RAG 吗"的答案，在写第一行代码前就定了：

| 问题 | 如果是"是" | 结论 |
|---|---|---|
| 这些知识模型**本来就会**吗（通用常识、公开常识）？ | 是 | **别建库**，直接问 |
| 语料只有**几十页**吗？ | 是 | **塞进上下文**（甚至一个长 `system_prompt`） |
| 数据是**结构化**的（表、订单、库存）？ | 是 | **SQL / Text2SQL**，不要向量化 |
| 查询是**精确匹配**（编号、报错码、法条、SKU）？ | 是 | **关键词检索**往往强过向量 |
| 语料大、非结构化、需要**按语义找**？ | 是 | ✅ **这才是该建向量库的场景** |

**为什么要这么教？**因为"把数据库向量化"是 web 开发者最常犯的错——你会天然觉得"都要上向量库"。实际上电商库存、订单状态这类东西，`SELECT ... WHERE sku = ?` 比任何 embedding 都准、都快、都便宜。

**示例 `12_mini_project_coffee_shop.py` 就是这个判断的样板**：店规只有 3 条，直接放进 `system_prompt`：

```python
RULES = """
- 营业时间：周一至周五 08:00-20:00；周六 09:00-22:00；周日休息。
- 会员：单次消费满 100 元可注册，1 元记 1 分，满 500 分换中杯拿铁一杯。
- 退款：饮品制作前可全额退；已制作完成不退；超过 500 元需店长审批。
"""
```

**3 条规则建向量库是工程笑话。**语料涨到几百上千条、且一直在变，才轮到第 09 章的东西。

## 概念：三种 RAG 架构（先选架构，再写代码）

官方给了三分法，这个分类比记 API 重要：

| 架构 | 检索时机 | 控制性 | 适合 |
|---|---|---|---|
| **2-Step RAG** | 永远在生成之前，固定一条链路 | 高、延迟稳定 | 问答型客服、FAQ |
| **Agentic RAG** | 模型**自己决定**要不要查、查什么 | 灵活、延迟不定 | 需要多轮查、需要组合工具 |
| **Hybrid RAG** | 固定链路 + 查询改写 / 结果校验 | 平衡 | 检索质量不够、问题表达模糊 |

**一句核心认知**：今天做 RAG ≈ **给 agent 一个"能查外部资料"的工具**。所以"RAG"和"工具调用"不是两件事——`09_rag_agent.py` 就 10 行把这个说清了：

```python
@tool
def search_rules(query: str) -> str:
    """查询咖啡店的内部规则（营业时间、会员、退款等）。query 用中文自然语言。"""
    docs = RETRIEVER.invoke(query)
    if not docs:
        return "知识库里没有找到相关内容。"
    return "\n".join(f"[{d.metadata['source']}] {d.page_content}" for d in docs)
```

**检索包成工具**，好处是你立刻获得了第 03 章学的所有东西：模型自己决定查几次、可以带多个检索源、可以和其他工具组合、出错能回灌。

## 跟着做

```bash
cd examples
uv run python 09_rag_agent.py
```

例子会问三个问题，**第三个才是重点**：

| 问题 | 知识库里有没有 | 期望行为 |
|---|---|---|
| 你们周六几点关门？ | 有 | 查出"09:00-22:00" |
| 满多少分可以换咖啡？ | 有 | 查出"500 分" |
| **你们卖咖啡豆吗？** | **没有** | **说"不知道"，绝不编造** |

输出会把过程打出来，你能看到"检索了什么、查到了什么、怎么答的"：

```
  🔍 检索: {'query': '营业时间'}
  📄 查到: [营业规则] 营业时间：周一至周五 08:00-20:00...
  💬 回答: 我们周六 09:00 到 22:00。
```

**为什么第三个问题最值钱？** 因为"编造"是 RAG 最常见的失败模式，而它不会报错——它会给你一段看起来很专业的假话。防它的手段是两个：

1. **工具说明 + system_prompt 里明确"查不到就说不知道"**（示例里都写了）
2. **元数据带上来源**（`[营业规则]`），让人和评测都能核对依据

## 概念：构建块（你只需要认这五个）

| 环节 | 工具 | 说明 |
|---|---|---|
| 文档对象 | `Document(page_content=..., metadata=...)` | **`metadata` 是后面所有过滤、溯源的基础** |
| 切分 | `RecursiveCharacterTextSplitter(chunk_size=, chunk_overlap=)` | 真实项目 300–800 字，重叠 10–20% |
| 向量化 | embedding 模型（见下方⚠️，示例会按配置自动选） | 换模型 = 全量重灌（见第 09 章） |
| 存储 | `InMemoryVectorStore` → Chroma → pgvector | 见第 09 章的三档 |
| 检索 | `.as_retriever(search_kwargs={"k": 2})` | `k` 别贪大，噪音比缺失更伤 |

**切分的大小是一个权衡**：块太大 → 检索不准（一堆无关内容一起进来）；块太小 → 丢上下文（"满 500 分"和"会员积分"被切开）。示例用 120 是为了演示，真实项目拿你自己的语料试 300/500/800 比一比。

### ⚠️ 一条很多人到上线才发现的现实：embedding 是**另一条供应链**

你很容易默认"我有 Key，所以什么都能调"。不是的：

**Agnes 官方文档列出的端点只有 `chat/completions`、`responses`、`messages`（文本）、`images/generations`（图像）、`videos`（视频）——没有 `/embeddings`；它的模型清单里也没有 embedding 模型。**

也就是说：**你的 chat Key 和算向量的 Key 是两码事。** 这件事只在 RAG 上暴露，而 RAG 往往又是你第一个"看起来能用"的功能，所以很容易到索引阶段才磞。

同样的话有更普遍的版本：**别假设一个供应商什么都给你。** 你要分别确认三类能力：

| 能力 | 干什么用 | Agnes 有吗 |
|---|---|---|
| Chat / 工具调用 | 所有 agent 逻辑 | ✅ 有 |
| Embedding | 建向量索引、语义检索 | ❌ 文档里没有 |
| 图像/视频生成 | 多模态输出 | ✅ 有（你以后会用到） |

所以示例的做法是（`_shared.py` 的 `get_embeddings()`）：**不配置就用假 embedding 把链路跑通，配置了就换真的**。

```bash
# 不填 → 假 embedding（无语义，只看流程）：能跑，不用钱
# 想真效果 → 随便找一家 OpenAI 兼容的，或用本地模型（fastembed / Ollama）
EMBEDDING_MODEL=text-embedding-3-small
EMBEDDING_API_KEY=sk-...
```

**这个设计本身就是一条工程建议**：embedding 必须是一个可替换的实现（接口），不能硬编码在业务逻辑里。因为你很可能会为了成本、合规、离线部署而换掉它——**而换掉它的代价是全量重灌**（第 09 章）。

## 自己动手改

1. **让"不知道"变成可验收**：把第 3 个问题改成 `"你们的会员卡能退吗？"`（知识库里没写这条）。如果它编了，就在 `system_prompt` 里加一句"如果检索结果里没有明确依据，直接回答'这个我不确定，帮您转人工'"。**这就是最小规模的迭代循环。**
2. **关掉工具看后果**：把 `tools=[search_rules]` 改成 `tools=[]`，重跑那三个问题。你会看到它凭训练数据编答案——**这就是"没有知识库"的样子**。（顺便：如果你的问题它居然都能答对，那就说明你根本不需要知识库，回到五问决策法。）
3. **加一个"知识库版本"字段**：给每个 `Document` 的 metadata 加 `{"version": "v2"}`，入库时把它带上，检索时按它过滤（写法注意：不是所有向量库都吃字典语法，见第 09 章那个坑）。这是上线后**回滚知识库**的关键手段。
4. **改 `k` 值**：`k=1`、`k=2`、`k=5` 各跑一遍，看答案里是否出现不相关内容。**这就是"检索质量"最朴素的评测。**

## 坑

- **一上来就建库**：先做五问决策，可能直接省掉几天。
- **把结构化数据灌进向量库**：用 SQL。真的。
- **没有"我不知道"的出口**：模型一定会编，因为默认行为是"给一个回答"。
- **切完分就不管了**：块大小和重叠要拿你的语料试出来，别照抄示例里的数字。
- **没有来源 metadata**：出了问题你无法定位，评测也无从下手。
- **把灌数据写在 agent 运行里**：每次启动都重新 embedding，又慢又贵。**灌数据必须是独立、可重跑的脚本**（第 09 章详述）。
