# 第 11 章：工程化——让它能上生产

## 本章目标

1. 建立**评测**：改一版 prompt 之后，你知道自己是变好还是变差
2. 用 trace 做定位，而不是靠 `print` 猜
3. 用**中间件**把重试、脱敏、摘要、限流这类横切关注点收口
4. 处理上下文、成本、安全这三件"demo 阶段看不出来、上线就出事"的事
5. 知道**流式输出**、前端接入与部署的入口在哪（你的主场）

**本章没有配套例子**——因为它的产物是**你自己的项目里的文件**（评测脚本、测试、清理策略）。示例里的 `run_all.py` 是它的最小形态。

---

## 概念：为什么"评测"排在第一位

先看一个你会遇到的场景：

```
改了一版 system_prompt，感觉回答更好了 → 上线
三天后客服反馈："它现在老是把退款规则答错"
```

**"感觉更好"是不可复现的证据。**智能体开发和 web 开发最大的差别在这里：web 有类型、有测试、有 500 报错；而 prompt 改动**不会报错**，只会悄悄变差。

所以工程化的第一件事不是监控、不是部署，是：**造一个能重复跑的评测集。**

### 最小可用评测（今天就能写）

不需要任何评测框架，一个 `eval.py` 就够：

```python
"""最小评测：固定问法 + 断言。改动 prompt / 模型后重跑，看通过数变化。"""
CASES = [
    # (输入, 断言函数)
    ("你们周六几点关门？", lambda ans: "22:00" in ans or "22" in ans),
    ("满多少分可以换咖啡？", lambda ans: "500" in ans),
    ("你们卖咖啡豆吗？", lambda ans: any(k in ans for k in ("不确定", "没有", "不卖", "转人工"))),
    ("退 1280 元", lambda ans: "审批" in ans or "人工" in ans),          # 大额必须提审批
]

def run() -> None:
    passed = 0
    for question, check in CASES:
        answer = ask(question)                    # 你的 agent 调用
        ok = check(answer)
        passed += ok
        print(f"{'✅' if ok else '❌'} {question}\n    {answer[:80]}")
    print(f"\n通过 {passed}/{len(CASES)}")

if __name__ == "__main__":
    run()
```

**关键设计**：

- **断言写在"行为"上，不写在"措辞"上**。别断言 `answer == "周六营业到22:00"`（模型换个说法就挂），要断言"包含 22"、"包含'不确定'"这类**语义特征**。
- **断言要覆盖"不该发生的事"**：编造、越权、跳过审批。**这类断言比"答对了"重要得多。**
- 初始集 **10–20 条就够**，来源就是"你手动测过的那几条"。以后每发现一个 bug，就往里加一条——**评测集自然会长大**。

```bash

```

示例目录里 14 个脚本、每个一个概念（`00` 环境自检 + `01`–`13` 概念示例），跑完给一张结果表——这就是"回归测试"的形态。**你以后自己的项目也应该有这么一个脚本。**

## 概念：trace（没有它你就在猜）

```bash
# examples/.env
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_...
```

trace 里你要看的四样东西：

| 看什么 | 用来定位 |
|---|---|
| **完整输入** | 它到底看到了什么上下文（含自动注入的 system prompt 和工具 schema） |
| **token 数** | 哪一步在烧钱、上下文什么时候膨胀 |
| **嵌套调用链** | 模型 → 工具 → 再模型的顺序对吗？有重复调用吗？ |
| **耗时** | 慢在哪一步 |

想用自建链路（不上 LangSmith），可以用 OpenTelemetry 导出到你的可观测平台——官方支持 OTel。

**一个实用习惯**：每次改 prompt，**先看一眼 trace 里"输入"变了没有**。很多"prompt 没效果"的情况其实是"新加的指令根本没进上下文"。

## 概念：上下文工程（80% 的效果问题在这层）

第 03 章你看到过：循环每转一轮，消息列表就长一截。**这就是智能体最大的工程挑战。**

| 症状 | 手段 |
|---|---|
| 上下文越来越长，变慢变贵 | **裁剪**：只保留最近 N 轮 + 早期摘要 |
| 长对话细节丢失 | **摘要压缩**：旧对话压成一段摘要 |
| 关键约束被遗忘 | **把约束放系统消息**，别混在长历史里 |
| 多任务互相干扰 | **子智能体隔离上下文**（第 10 章 subagents） |
| 同一个大文档重复发送 | **把大内容落盘/入知识库**，上下文里只放引用 |

`create_agent` 接受 **middleware** 参数，摘要/裁剪这类能力就是以中间件形式挂上去的（官方有现成实现，也可以自己写）。

⚠️ **写中间件之前先验证 API**——中间件的具体类和钩子名会随版本变化，**不要照抄博客**：

```bash
uv run python -c "
from importlib.metadata import version
import inspect
# langgraph 没有 __version__ 属性，只能这样查（实测：langgraph 1.2.12 会报 AttributeError）
print(version('langchain'), version('langgraph'))
from langchain.agents import create_agent
print(inspect.signature(create_agent))          # 看有没有 middleware 参数、有哪些参数
import langchain.agents.middleware as m
print([n for n in dir(m) if not n.startswith('_')])   # 看现成的中间件有哪些
"
```

**这条命令是你以后自己写代码时的第一动作**：两分钟确认签名，胜过半小时试错。

## 概念：中间件——横切关注点的收口

你在 Express / Laravel 里不会把"重试、脱敏、日志"抄进每个 controller。agent 也一样：**中间件把这类横切逻辑挂在 agent 的生命周期上**，业务节点保持干净。

| 钩子 | 时机 | 你的直觉 |
|---|---|---|
| `before_agent` | 整个 agent 开始前一次 | 全局中间件 |
| `before_model` | 每次模型调用前 | 请求预处理 |
| `wrap_model_call` | 包住模型调用 | 重试 / 熔断 / 换模型 |
| `wrap_tool_call` | 包住工具调用 | 工具层兜底 |
| `after_model` | 每次模型返回后 | 响应校验 / 护栏 |
| `after_agent` | 结束后一次 | 收尾清理 |

现成的中间件很多，常用的这几个（下面用到的参数都在实测版本上 `inspect` 过）：

```python
from langchain.agents import create_agent
from langchain.agents.middleware import (
    PIIMiddleware,              # 脱敏：邮箱 / 信用卡 / IP …
    SummarizationMiddleware,    # 上下文太长就摘要压缩
    HumanInTheLoopMiddleware,   # 工具级人工审批
    ModelRetryMiddleware,       # 模型调用失败重试（指数退避）
    ModelFallbackMiddleware,    # 主模型不可用就换备用
    ToolCallLimitMiddleware,    # 工具 / 轮次硬上限
    TodoListMiddleware,         # 长任务的待办清单
)

agent = create_agent(
    model=..., tools=[...],
    middleware=[
        PIIMiddleware("email", strategy="redact", apply_to_input=True),
        SummarizationMiddleware(model=..., trigger=("tokens", 4000)),
        ToolCallLimitMiddleware(thread_limit=20),   # ★ 硬上限写在代码里，不写在 prompt 里
        ModelRetryMiddleware(max_retries=2),
    ],
)
```

**为什么它比"写进 prompt"可靠**：中间件是代码，能被测试、能被审计；prompt 是建议，模型可以选择不听。第 03 章的"步数上限"、第 07 章的"审批闸门"、第 09 章的"权限过滤"——到了 agent 形态，都应该落在中间件或工具层。

## 概念：测试——测什么

| 层 | 测什么 | 怎么测 |
|---|---|---|
| **路由/业务规则** | 纯函数：`route_by_amount(...)` 返回哪个节点 | 普通单元测试，**必测** |
| **工具** | 参数校验、失败返回、路径沙箱 | 单元测试（不调模型） |
| **图结构** | 图能编译、节点名和边没写错 | `builder.compile()` + 走一遍最小输入 |
| **中断/恢复** | 中断后状态在库里、恢复走对分支 | 集成测试（用 SQLite） |
| **端到端** | 评测集（上面那个 `eval.py`） | 定期跑，**标注通过率** |

**最值钱的两条纪律**：

1. **凡是不依赖模型的逻辑，一律写成纯函数并单元测试**。路由、阈值、参数校验——这些是"业务正确性"的地基，不该被模型的不确定性污染。
2. **凡是有权限含义的过滤，必须有测试**。比如"租户 A 的检索结果里不能出现租户 B 的数据"——漏了就是越权，而且线上不会报错。

## 概念：成本、限流、容错

| 风险 | 措施 |
|---|---|
| 无限循环 / 疯狂调工具 | **步数上限**（第 03 章的 `MAX_STEPS`）、`recursion_limit`、单次任务 token 预算 |
| 供应商限流（429） | 指数退避重试、请求队列、多 Key/多供应商 |
| 单点超时 | 超时 + 降级（返回"稍后重试"而不是挂住） |
| 重复副作用 | 幂等设计（第 07 章） |
| 上下文爆掉 | 裁剪 + 摘要（上面） |
| 成本失控 | trace 里盯 token；给每类任务设预算上限 |

**重要心态转变**：你现在有免费额度，**不用担心钱，但一定要有上限**。因为上限不是为了省钱，而是**为了不让系统跑崩**——没有上限的循环在线上就是"服务不可用 + 账单爆炸 + 用户投诉"三连。

## 概念：流式输出——把过程交给前端

agent 跑一轮可能要几秒到几分钟，前端不可能干等。LangGraph 的**事件流**把过程实时吐出来（v1 起推荐 `stream_events`）：

```python
config = {"configurable": {"thread_id": "chat-001"}}

stream = graph.stream_events(
    {"messages": [{"role": "user", "content": "..."}]},
    config,
    version="v3",          # 事件流协议版本
)

for chunk in stream.messages:   # 逐条消息 / 逐 token
    print(chunk)

stream.interrupted              # 是否停在 interrupt() 上
stream.interrupts               # 待人回答的内容（直接喂给审批 UI）
stream.output                   # 最终状态（等价于 invoke 的返回值）
stream.values                   # 状态快照的逐步变化
```

实测要点（langgraph 1.2.12）：

- **`stream.interrupts` / `stream.interrupted` 比 `result["__interrupt__"]` 直白得多**——做人工审批界面时优先用它
- v3 协议在当前版本仍会打印一条 `LangChainBetaWarning: The v3 streaming protocol on Pregel is experimental.`：**是提示，不是错误**，官方文档已经把它当推荐路径
- 流式不只是"炫酷"：它同时是你的**调试工具**（过程可见）和**前端体验**（先出字）

## 概念：前端接入（你的主场）

你有前端背景，这块对你不是"学习"而是"选型"。官方给了整套前端方案：

| 需求 | 用什么 |
|---|---|
| 快速验证一个聊天界面 | **Agent Chat UI**（开箱） |
| 可视化看流程跑了什么 | **LangSmith Studio**（建议第 2 周就装上） |
| 自己的 React 界面 | AI Elements / assistant-ui / CopilotKit 等 |
| 生成式 UI（模型决定渲染什么组件） | Generative UI |
| 人工审批界面 | HITL 组件的固定套路：展示中断载荷 → 三个按钮（批准/编辑/拒绝）→ `Command(resume=...)` |
| 断线重连的流 | 流式 API + 重连后按 `thread_id` 拉回状态 |

**你要注意的关键点**：前端不再是"请求-响应"，而是**"事件流 + 状态快照"**。因为流程可能中断等你回答、可能跑很久。**用 WebSocket / SSE 的心智去做，不要用 `fetch` 的。**

## 概念：部署（知道入口就行）

图写对之后，"上线"主要是把它包成服务。这一层现在只需要知道入口：

| 你要什么 | 去哪 |
|---|---|
| 本地起一个带 UI 的服务联调 | 官方 CLI 的 **Run a local server**（`langgraph dev` 那套，需装 LangGraph CLI） |
| 托管到云上 | **Deployment**（LangSmith 云，从 GitHub 仓库部署，基础设施由它管） |
| 前端要直连的服务端 API | **Server API**：threads / runs 这些资源本来就是按"图即服务"设计的 |
| 长任务、后台运行、定时 | 官方有专页（后台运行 / cron 类支持） |

**先别深挖这一层。**能把图编译跑通、评测过、trace 打开，你就已经跨过 90% 的学习者；部署是"把它搬上去"，不是新的智能体知识。

## 自己动手改（这一章的作业是你项目的文件，不是示例）

1. **写 `eval.py`**：从你的 agent 里挑 10 条问法，加断言，跑出通过率。**然后把通过率记在 `notes.md` 里。**
2. **制造一次回归**：故意在 `system_prompt` 里删掉"查不到就说不知道"，重跑 `eval.py`。**你会亲眼看到通过率下降**——这一眼比读十页"为什么需要评测"有用。
3. **加权限测试**：如果做过第 09 章的多租户过滤，写一个断言"租户 A 查不到 B 的数据"，跑通。
4. **读一次 trace**：找一个你答错的案例，在 trace 里找出**它当时看到的上下文**，写出"它为什么会这么答"的一句话结论。
5. **检查安全清单**：你的项目里有没有 `shell=True`？有没有路径拼接？高危操作有没有审批？有没有把工具参数当可信输入？

### 一个真实踩到的例子：模块级副作用

写 `09_rag_agent.py` 时我一开始是这么写的：

```python
RETRIEVER = build_retriever()      # ← 模块被 import 的一瞬间就去建索引了
```

看起来只是“少写一层函数”，但后果是：

- 任何人 `import` 这个文件就会触发**网络请求**（真 embedding 要调 API）
- 没配 Key 就直接**崩在 import 行**，报错位置跟你真正的问题毫无关系（实测报的是 `OpenAIError: Missing credentials`，跟 RAG 逻辑一点关系都没有）
- 测试没法 import 它，也就没法单独测那个检索函数

**规矩：初始化可以慢，但不能有副作用、不能联网。** 把建索引包进函数，由入口显式调用；真需要共享，用"惰性初始化 + 缓存"，而不是模块顶层直接执行。

这是同一个老道理的 Python 版：**不要在 import 时干活**（你在前端也见过它——模块顶层调 `window`、在 `import` 时发 `fetch`）。

## 坑

- **没有评测就调 prompt**：三天后你无法解释为什么变差，也无法回滚。
- **模块级副作用**：`import` 就联网 / 建索引 / 读文件。测试没法跑，报错还指向无关的行。
- **硬编码具体供应商**：embedding、向量库、模型都可能是"以后要换"的，硬编码就意味着重写。
- **断言措辞**：`answer == "..."` 这种断言会让你不断"为了测试而改测试"。
- **忘了测权限**：漏一个 `filter` 就是越权，且不报错。
- **中间件 API 照抄博客**：先用 `inspect.signature` 验证（上面那条命令）。
- **把"上限"只写在 prompt 里**：模型不会遵守。用 `ToolCallLimitMiddleware` 或条件边里的计数器。
- **以为 v3 流式的 `LangChainBetaWarning` 是报错**：它是提示；但版本升级后 API 可能变，前端对接留一层适配。
- **把 `stream_mode` 老 API 和 `stream_events(v3)` 混用**：两套心智（一个看增量、一个看事件），挑一套用到底。
- **在 trace 里只看答案，不看输入**：问题几乎总在输入侧。
- **不留清理策略**：checkpoint 和向量库都会无限增长（第 06、09 章）。
- **把 `shell=True` 留给"以后再改"**：注入不需要等你准备好。
