# 第 09 章：向量库与检索质量

## 本章目标

1. 三档存储选一个用：内存 → 本地持久 → **pgvector（生产）**
2. 掌握"元数据过滤"这个多租户/权限隔离的钥匙
3. 按顺序提升检索质量，而不是一次全上（一次全上你无法判断谁起作用）
4. 处理新手最大盲区：**增量更新与重灌**

**配套例子**：`examples/04_index_offline.py`（**离线可跑，用假 embedding，现在就能练**）

---

## 概念：选型就三档

| 档 | 用什么 | 包 | 什么时候 |
|---|---|---|---|
| 开发/测试 | `InMemoryVectorStore` | `langchain-core` 内置 | 跑通链路、写测试 |
| 本地持久 | `Chroma(persist_directory=...)` | `langchain-chroma` | 单机原型、桌面应用 |
| **生产** | **`PGVector`（Postgres 扩展）** | `langchain-postgres` | 有并发、要备份、要事务 |

**为什么主线讲 pgvector 而不是"某专用向量数据库"？** 三个理由，正好都是你写 PHP 时的经验：

1. **它是扩展，不是新数据库**。你已经有 Postgres 了，加个扩展即可——`CREATE EXTENSION vector`。
2. **它能和业务表放同一个库**。做 join、做事务、做权限，都是 SQL 的老本行。多一个系统就多一份运维。
3. **元数据过滤走的是 SQL**，`WHERE tenant_id = ?` 这种你闭着眼都能写。

对等替代（等你有特殊需求再看）：`Qdrant` / `Pinecone` / `Milvus` / `Weaviate` / `MongoDB Atlas`（已在用 Mongo 的话）。**先别选专用库，除非你被逼到那一步。**

### pgvector 三分钟起步

```bash
# 起一个带 pgvector 的 Postgres（端口、密码自己改；注意镜像 tag 按官方文档选）
docker run --name pgvector-dev \
  -e POSTGRES_PASSWORD=secret \
  -e POSTGRES_DB=agent \
  -p 6024:5432 -d pgvector/pgvector:pg17

uv add langchain-postgres
```

```python
from langchain_postgres import PGVector

store = PGVector(
    embeddings=embeddings,
    collection_name="coffee_rules",        # 一个 collection 类似一张表
    connection="postgresql+psycopg://postgres:secret@localhost:6024/agent",
    use_jsonb=True,                        # 元数据存 jsonb，过滤更灵活
)

store.add_documents(docs, ids=[d.metadata["id"] for d in docs])
store.similarity_search_with_score("营业时间", k=3)      # 带相似度分数
store.delete(ids=["rule-0"])
retriever = store.as_retriever(search_type="mmr", search_kwargs={"k": 3})
```

### ⚠️ 一个必须提前想好的代价

**pgvector 集成不支持 schema 变更时的数据迁移。** 意思是：改了 embedding 维度、改了元数据结构，**要重建表、重灌数据**。

所以你必须**在第一天就想好**：embedding 模型、维度、metadata 字段。否则未来某次升级要停机重灌——语料越大越痛。

四件最容易搞错的事，这里全能看清：

### 1. 切分

```
切分结果：5 块        # 具体块数取决于 chunk_size，重点是你能看到切到哪
```

### 2. 元数据过滤（多租户隔离的钥匙）

```python
# InMemoryVectorStore 的 filter 只接受【可调用对象】，不接受字典！
only_hours = store.similarity_search("营业时间", k=20, filter=by_metadata(category="营业时间"))
other_tenant = store.similarity_search("营业时间", k=20, filter=by_metadata(tenant="shop-999"))
```

输出（**命中数会因切分结果而不同，重点看趋势**）：

```
  只看 category='营业时间' → 命中 2 条
  换个 tenant='shop-999' → 命中 0 条（看不到别家的数据 ✅）
```

**"看不到别家的数据"是靠代码保证的，不是靠模型自觉。**这就是为什么我在第 03 章说"prompt 不是权限控制"。

#### ⚠️ 这里有个实测踩到的坑，必须记住

`InMemoryVectorStore` 的 `filter` 参数**只接受 callable**（`(Document) -> bool`）。你要是习惯性地传元数据字典：

```python
store.similarity_search("营业时间", k=20, filter={"category": "营业时间"})
# TypeError: 'dict' object is not callable
```

这不是你写错了——是 `langchain-core 1.6.4` 的真实行为：它内部把参数命名成 `filter`，把内置函数 `filter()` 遮盖了，然后又真的去调用它。`04_index_offline.py` 里有一段把这个报错打印出来的演示，**建议你亲手跑一次**。

**真正的教训是：过滤语法没有跨库统一标准。**

| 你在哪 | 过滤怎么写 |
|---|---|
| `InMemoryVectorStore` | `filter=lambda doc: doc.metadata.get("x") == "y"` |
| Chroma / PGVector / MongoDB | 元数据字典 + 操作符（下表） |
| `as_retriever(search_kwargs=...)` | 只是把参数透传给向量库，**传什么取决于你用哪个库** |

所以**不要把过滤语法硬编码进业务层**。正确做法：业务层只表达"要哪个租户的数据"，具体语法收敛到一个适配函数里（`04_index_offline.py` 的 `by_metadata()` 就是这个思路的最小版）。这样从内存库换到 pgvector 时你只改一个函数，而不是改遍全项目。

常用操作符（**各向量库支持程度不同，pgvector/Chroma 较全；内存库不支持**）：

| 操作符 | 含义 | 典型用途 |
|---|---|---|
| `$eq` / `$ne` | 等于 / 不等于 | 租户隔离、状态过滤 |
| `$in` / `$nin` | 在 / 不在集合 | 多部门、多标签 |
| `$gt` / `$lt` / `$between` | 范围 | 时间窗口、金额区间 |
| `$like` | 模糊 | 标题匹配 |
| `$and` / `$or` | 组合 | 复杂权限 |

### 3. 更新：同 id 覆盖

```python
store.add_documents([Document(page_content="营业时间：周六改为 10:00-23:00。",
                              metadata={"id": "rule-0", ...})],
                    ids=["rule-0"])      # ★ 同 id → 覆盖，不是新增
```

输出会告诉你"数量不变"——**这就是更新机制**。没有稳定 id 的向量库，等于无法更新。

### 4. 删除

```python
store.delete(ids=["rule-0"])
```

**这一条对应"源文档被删掉了"的场景**，第 5 节会讲它的策略价值。

## 概念：检索质量——按顺序升级

光有向量相似度是不够的。但**别一次全上**，否则出问题你不知道是谁的功劳：

| 顺序 | 手段 | 解决什么 | 代价 |
|---|---|---|---|
| ① | 纯向量相似度 | 基线 | 最低 |
| ② | **MMR**（最大边际相关） | 结果太重复、全是一个主题 | 低，`search_type="mmr"` |
| ③ | **元数据过滤** | 权限、时效、"只看 v2 文档" | 低，而且必须做 |
| ④ | **混合检索**（关键词 + 向量） | 编号、专有名词、精确匹配 | 中，需要额外索引 |
| ⑤ | **重排 Rerank** | 语义相近但没用，排序不准 | 中，多一次模型调用 |

集成入口（挑你用的那家，别硬记）：

- 混合检索：`MongoDBAtlasHybridSearchRetriever`、`ElasticsearchRetriever`、`BM25Retriever` 类
- 重排：各家 reranker 集成（Cohere / Pinecone / Contextual AI / `WatsonxRerank` 等）

**上线顺序**：先 ①②③，跑评测记录；不够再加 ④，再不够加 ⑤。**每次只加一层，加完记录指标变化**——这就是第 11 章"评测"要解决的事。

## 概念：增量更新（新手最大盲区）

知识库不是"跑一次就完事"的脚本。它有三个必须有自己的策略的事件：

| 事件 | 触发 | 你要做什么 |
|---|---|---|
| **源文档改了** | 有人编辑了 FAQ | 按稳定 id 覆盖那几条（`add_documents(..., ids=[...])`） |
| **源文档删了** | 内容下线 | `delete(ids=[...])`，**否则过期内容会一直毒害答案** |
| **换 embedding 模型** | 想升级到更强的 | **全量重灌**（新旧向量不可比，混着用等于随机） |

三条工程纪律：

1. **灌数据脚本要独立、可重跑**（`scripts/index_docs.py`），**不要写在 agent 启动流程里**。
2. **id 要稳定且来自源数据**（文件路径 + 行范围、数据库主键、内容 hash），别用随机 uuid。
3. **记录索引元信息**：用了哪个 embedding 模型、哪次灌的、语料版本。否则三个月后没人敢动它。

> ⚠️ **v1 的 API 迁移坑**：传统"索引 API"（`indexes`）在 v1 已迁到 `langchain-classic`。
> 照着老博客抄 `from langchain.indexes import ...` 会失败——用新路径，或者干脆自己写 upsert 逻辑（**推荐后者，更可控**）。

## 坑

- **用随机 id**：无法更新、无法删除，库里会越堆越多脏数据。
- **只在本地内存跑通了就上生产**：进程一重启知识库没了，而你的测试会全部通过。
- **换了 embedding 只重灌一半**：新旧向量混在一个 collection 里，检索结果会变得诡异且难以排查。
- **过滤字段忘了带**：多租户场景下，漏加 `tenant` 过滤 = **越权读到别家数据**。这类错误要写测试（第 11 章）。
- **语料切分大小照抄示例**（示例是 60，真实项目 300–800）。
- **`indexes` 用旧导入路径**：v1 已迁到 `langchain-classic`。
