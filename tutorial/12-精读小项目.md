# 第 12 章：精读一个完整小项目

## 本章目标

1. 看清"五个零件怎么拼成一个能交付的东西"
2. 学会**审阅**一个 agent 项目（问对问题比读懂代码重要）
3. 明确它离"生产可用"还差哪几步——**这一步就是你毕业项目的作业清单**

**配套例子**：`examples/12_mini_project_coffee_shop.py`（需要 Key）

---

## 概念：这是一个"最小可交付形态"

前面 11 章每章只讲一个零件。这个文件把它们拼起来：

| 零件 | 在这个项目里 | 解决什么 |
|---|---|---|
| **LangGraph 状态机** | `classify → (answer \| approve) → finalize` | 流程可控、能分支 |
| **结构化输出** | `classify` 节点里的 `with_structured_output(Intent)` | 意图识别不靠正则 |
| **工具** | `lookup_order` | 回答有依据 |
| **知识** | `RULES` 常数（只有 3 条，直接进 prompt） | 不编造 |
| **人工审批** | `approve` 里的 `interrupt()` | 大额操作要人点头 |
| **记忆** | `InMemorySaver` + `history` 字段（`add` reducer） | 同一客人跨轮记得 |

**注意它没有的东西**：没有多智能体、没有 MCP、没有向量库。**一个能交付的小项目，本来就不需要这些。**这一点值得记住——教程教你零件，不代表你要把所有零件都装上。

---

## 跟着做

```bash
cd examples
uv run python 12_mini_project_coffee_shop.py
```

四轮对话，每轮验证一个零件：

| 轮次 | 输入 | 走哪个分支 | 验证什么 |
|---|---|---|---|
| 1 | 你们周六几点关门？ | `answer` | 知识在 prompt 里，不编造 |
| 2 | 我这杯拿铁做错了，想退款 38 元 | `approve`（自动） | 小额自动放行 |
| 3 | 团建订的 1280 元想整单退掉 | `approve`（**中断**） | 人工审批生效 |
| 4 | 再问一下，我刚才是退了多少钱？ | `answer` | `history` 字段（记忆） |

第 3 轮你会看到：

```
  [classify] 意图=退款申请 金额=1280
  [approve] 1280 元超阈值，等待人工审批
  ⏸  等待人工：同意退款 1280 元吗？
  人工回答：同意
  💬 退款 1280 元已通过审批，正在处理。
```

---

## 看懂结构（这张图要背下来）

```
START → classify ─┬─ 咨询 → answer  ──┐
                  └─ 退款 → approve ──┴→ finalize → END
                              ↑
                       超阈值时 interrupt() 停在这里
```

对照代码：

```python
builder.add_edge(START, "classify")
builder.add_conditional_edges("classify", route_after_classify)   # ★ 分流
builder.add_edge("answer", "finalize")
builder.add_edge("approve", "finalize")
builder.add_edge("finalize", END)
return builder.compile(checkpointer=InMemorySaver())
```

三个值得学习的设计：

1. **分类和业务分离**：`classify` 只管分类，`route_after_classify` 是纯函数（可单测），业务节点只管各自的活。
2. **`history` 用 `add` reducer**：`Annotated[list[str], add]`。如果忘了 `add`，每轮的记忆都会把上一轮覆盖掉——**这是第 05 章那个坑的真实应用**。
3. **阈值是常量**：`APPROVAL_THRESHOLD = 500`，不在 prompt 里。**业务规则永远在代码里。**
4. **守卫写在分流函数里**：`route_after_classify` 不只比 `kind`，还要求 `amount > 0`。
   为什么需要这一道：实测（2026-09-24）第 4 轮那句"我刚才是退了多少钱？"会被模型
   判成**退款申请、金额 0**，原来的分流直接进 `approve` → **自动受理了一笔 0 元退款**，
   还把它写进记忆。分类永远可能错，所以"可执行 / 不可执行"的判定要再撑一道代码级的防线——
   这也是这个项目里唯一一个**被断言抓出来的真 bug**（"不该发生的事"比"答对了"更值得测）。

## 概念：怎么"审阅"一个 agent 项目

这是本章最重要的技能，比读懂具体代码更值钱。**拿到任何 agent 项目，问这六个问题：**

| # | 问题 | 为什么问 |
|---|---|---|
| 1 | **每个节点被喂了什么上下文？** | 上下文决定它能不能做对；塞太多则又慢又贵 |
| 2 | **它凭什么判断自己干完了？** | 是结构化判定，还是"扫关键词"？（**最容易出现脆弱设计的地方**） |
| 3 | **失败了谁负责纠偏？** | 有没有重试/重工路径？有没有上限？还是静默假装成功？ |
| 4 | **副作用在哪一步执行？** | 会不会因为中断重跑而重复执行？ |
| 5 | **权限边界靠什么保证？** | 代码过滤 / 沙箱 / 审批，还是 prompt 里的"请勿"？ |
| 6 | **改一版怎么知道没变差？** | 有没有评测集？没有 = 无法维护 |

**用这六问审阅 `12` 这个例子**，你会发现它第 2、5 条做得好（结构化意图 + 阈值在代码里），第 6 条基本没有（没有评测），第 1 条有改进空间（`RULES` 直接拼进 prompt，规则一多就会爆上下文）。

第 1 条还连带修过一个真问题：第 4 轮的追问曾经答不上来——回答节点只看得到当前这一句，
同一 thread 的历史压根没喂进去（`history` 字段存了，但没人用它）。现在 `answer` 节点
会把历史摘要拼进上下文。**这就是第 1 个审阅问题的实战：每个节点被喂了什么上下文？**

**这六个问题就是第 13 章毕业项目的验收标准。**

## 概念：它离生产还差什么

例子最后自己列了清单（**这是刻意的教学设计**，让你学会自己列）：

```
  ✅ 流程可控（状态机）+ 分支 + 人工卡点 + 断点续跑
  ✅ 意图识别用结构化输出，不用正则
  ⬜ 换持久 checkpointer：PostgresSaver → 重启不丢
  ⬜ 接真实向量库：语料超过几十条就上 pgvector
  ⬜ 评测：10-20 条固定问法 + 断言
  ⬜ Trace：LANGSMITH_TRACING=true
  ⬜ 重试上限：给循环设硬上限，超限转人工
```

按"上线必要性"排序，我的建议是：

1. **持久 checkpointer**（不换的话重启就丢所有会话）
2. **评测**（不做的后果是"无法维护"）
3. **上限**（不做的话线上会卡死）
4. **Trace**（不做的话排障靠猜）
5. **向量库**（**最后才轮到它**——先问五问决策法，语料没到规模就别上）

**注意第 5 项的排序。**这是新手最容易搞反的地方：他们第一件事就上向量库，最后才想起"我的服务重启会丢数据"。

## 自己动手改

1. **加一个"投诉"分支**：`Intent.kind` 加上 `"投诉"`，新增一个 `escalate` 节点（比如"已转人工，稍后联系您"），走条件边。**练手：改 schema → 改路由 → 加节点 → 加边，四步都碰一遍。**
2. **把 `RULES` 换成检索**：规则加到 20 条（自己编），拼进 prompt 就太长了；改成第 08 章的 `search_rules` 工具。**对比两次的 trace：token 数和准确率各有什么变化？**
3. **把 `InMemorySaver` 换成 `SqliteSaver`**，然后分两次运行——第一次聊两句就退出，第二次用同一个 `thread_id` 问"我刚说了什么"。**这就是生产形态。**
4. **写 5 条评测**：按第 11 章的模板，给这个项目写 `eval.py`。**这是毕业项目的提前演练。**
5. **故意破坏记忆**：把 `history` 的 `Annotated[list[str], add]` 改成 `list[str]`（去掉 reducer），重跑第 4 轮，看记忆消失。**第 05 章的坑，在真实项目里再踩一次。**
6. **拆掉金额守卫**：把 `route_after_classify` 里的 `amount > 0` 去掉，重跑第 4 轮——
   你会看到它把一句**提问**当成 0 元退款自动受理，还记进记忆（脚本的断言会当场红）。
   这类"不算崩但很危险"的 bug，只有语义断言抓得住。

## 验收问题

1. 这个项目用到了五个零件中的哪几个？为什么它**不需要**多智能体和 MCP？
2. `history` 字段的 reducer 去掉会怎样？
3. 第 3 轮的中断是怎么把"金额"和"诉求"传给人类的？
4. 用六问审阅法，这个项目哪两条做得好、哪两条薄弱？
5. 从"能演示"到"能上线"，五件事的正确排序是什么？为什么向量库排在最后？

---

## 坑

- **看到"完整小项目"就以为可以直接上线**。它省掉的恰恰是上线必需的（持久化、评测、上限）。
- **`RULES` 拼进 prompt 无限增长**：规则条数一多就是上下文炸弹，那时才该上 RAG。
- **所有分支都汇到 `finalize` 的空节点**：这里它只是留个统一出口；真实项目里 `finalize` 通常要做"记录、通知、写审计日志"。
- **`InMemorySaver` 用在真实客服里**：重启即失忆，用户会疯。
- **忘了给 `history` 用 `add`**：记忆静默失效，且不报错。
- **拿模型分类当唯一门禁**："我刚才是退了多少钱"被判成退款申请、金额 0，代码不兜底就自动受理了一笔 0 元退款。**分类可能错，可执行性要在代码里再判一次。**
- **状态里存了历史，节点却不读**：`history` 攒得好好的，回答节点却只看当前一句，追问全部答不上来。**存 ≠ 用。**
