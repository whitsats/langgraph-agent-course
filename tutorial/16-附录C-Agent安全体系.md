# 第 16 章：附录 C —— Agent 安全体系

> 前 15 章都在教你把 agent 做出来、做顺、做快。这一章讲怎么让它**不被打穿**。
> 核心立场先放这里：**洞不在模型里，在你的代码里**——在工具层、权限层、流程层。
> 所以这一章的"补丁"全部是工程手段（校验、白名单、范围约束、审批），没有一个是
> "在 prompt 里拜托模型别听坏人的"。

**骨架**：OWASP《Top 10 for Agentic Applications 2026》（2025-12-09 发布，
100+ 位专家评审，编号 ASI01–ASI10）。这是目前智能体安全最成体系的公开地图。
**建议用时**：1 天。
**配套例子**：`examples/16_agent_security_lab.py`（**离线可跑，不需要 Key**，已收编进 `run_all.py` 离线组）。

---

## 本章目标

1. 能对 agent 的安全威胁**分类**：直接注入 / 间接注入 / 工具链投毒 / 权限滥用 / 供应链……用的是 OWASP 的地图，不是零散新闻
2. 亲手复现四类攻击，并亲眼看到**代码层补丁**怎么拦住它们
3. 会用 **Least agency + 强可观测** 两条原则、**三个信任边界问题**设计自己的 agent

## 概念：安全地图——十条风险先认全

| 编号 | 风险 | 一句话 |
|---|---|---|
| ASI01 | Agent 目标劫持 | 骗 agent 改目标 / 跟随隐藏指令——整个多步流程被带偏，表面上还在"正常干活" |
| ASI02 | 工具滥用与利用 | 每个工具都合法，**组合**没人授权过（查敏感记录 → 写文件 → 外发邮件） |
| ASI03 | 身份与权限滥用 | agent 继承了共享账号 / 静态 Key / 完整用户会话，出错时"谁干的"都答不上 |
| ASI04 | 智能体供应链 | 被投毒的第三方 agent、MCP server、插件、prompt 模板——运行时供应链 |
| ASI05 | 意外代码执行 | 生成的 shell / SQL / Python 拿着生产凭据就跑 |
| ASI06 | 记忆与上下文投毒 | 往长期记忆、RAG 库、共享上下文里种脏数据，影响**未来**的会话 |
| ASI07 | 不安全的 agent 间通信 | 多 agent 之间的消息没有认证 / 完整性 / 防重放 |
| ASI08 | 级联失败 | 小错误在规划-执行链路里放大：幻觉端点 → 失败调用 → 更糟的调用（离线复现见第 17 章附录D） |
| ASI09 | 人机信任利用 | 用户过度信任流畅自信的 agent——被操纵的摘要、钓鱼式"建议" |
| ASI10 | 失控 agent | 凭据合法、行为正常，但已在 pursue 隐藏目标（数据外泄 / 污染同伴） |

OWASP 自己的观察值得记一句：**这十条里大半是"身份与授权问题穿了马甲"**。
所以下面两条原则、三个问题比背十条更重要。

---

## 概念：两条设计原则 + 三个信任边界问题

OWASP 在十条之前先给了两条原则，它们是"最小权限"在 agent 时代的进化：

| 原则 | 含义 | 你的直觉类比 |
|---|---|---|
| **Least agency（最小代理权）** | 不仅管 agent"能访问什么"，还管它"能**自主**做什么、多久才回头确认一次"。**自主权是挣来的，不是默认给的** | 新员工不给 root，先做只读，逐步放权 |
| **Strong observability（强可观测）** | 能回答：agent 在做什么、为什么做、用谁的身份做。没有它，最小权限只是盲目的风险削减 | 第 11 章的 trace + 审计日志 |

**任何信任边界上问三个问题**（用户输入进来时、调工具前、交给下一个 agent 时）：

1. **谁在行动？**——是独立的 agent 身份，不是借来的用户会话
2. **被授权做什么？**——有范围、有时限、可撤销
3. **事后能证明吗？**——审计痕迹把身份、决策、结果串起来

---

## 概念：提示注入的两张脸（ASI01 的主攻路径）

**直接注入**：用户输入里夹带"改目标"的指令。
**间接注入**：指令藏在**数据**里——检索结果、网页、邮件正文、工单。等"被读"的那一刻变成指令。

你有现成的类比，而且这个类比精确得可怕：

| Web 世界 | Agent 世界 |
|---|---|
| SQL 注入：用户输入直接拼进 SQL | 直接注入：用户文本直接拼进 prompt |
| **存储型 XSS**：恶意脚本先入库，被"渲染"时执行 | **间接注入**：恶意指令先入文档/网页，被"检索"时生效 |

间接注入比直接注入危险得多，因为**受害者根本不是攻击者**：投毒的人可以是一条
公开网页、一份共享文档的作者，中招的是后来检索到它的每一个会话。
Web 时代 XSS 的解法是"转义 + 上下文分离"，agent 时代的对应物是
**"外部内容一律是数据，不是指令"**——例子的实验 2 演示了这句话的具体形态。

---

## 概念：工具链投毒——管组合，不管单个（ASI02）

实验 3 的攻击轨迹：`search_orders → write_file(外发副本) → send_email`。
逐个看全合法；合起来是数据外泄。**每个工具都可能被授权过，这个组合没有。**

这就是为什么"每个工具都加了权限校验"不等于安全——校验是**点**上的，攻击是**线**上的。
解法都在流程层：允许的工具序列写死在图里（你第 05 章学的条件边恰好就是干这个的）、
数据带敏感度标签、外发动作一律人工审批（第 07 章）。

---

## 概念：最小权限——注入防不住时的兜底（ASI03）

实验 4 是全章最重要的一张表：**同一发攻击，两种权限，两种结局。**

| agent 手里的权限 | 被间接注入后 |
|---|---|
| 宽权限（读写文件 + 发邮件，现在的多数 demo） | ⚠️ 数据外泄成功 |
| 窄权限（只读 notes*，无外发工具） | ✅ 攻击无路可走 |

**注入能不能得手，最后取决于 agent 手里有什么权限。**这是你在设计时唯一
完全可控的变量：prompt 会被绕过、模型会被骗，但"工具集里根本没有 send_email"
这件事骗不了。落地动作：每个 agent 专用身份、工具级授权、时限与范围、高危动作走审批。

## 看懂输出

四个实验各看一行：

1. 实验 1 末尾 `发件箱：1 封 → ⚠️ 数据已外泄`——注入得手了，先接受这个事实
2. 实验 2 的 `secrets 是否被写进 feedback.log：⚠️ 是`——注意**用户的问题完全无害**，作恶的是检索到的文档
3. 实验 3 的"逐个看 ✅✅✅，合起来 ❌"——理解"组合攻击"四个字
4. 实验 4 的两行对比——窄权限下两条 `拦截：`，这就是代码层安全网的样子

## 概念：三层防线（把补丁系统化）

四个实验的补丁收拢成一张表，从外到里：

| 层 | 手段 | 对应实验 | 对应你学过的 |
|---|---|---|---|
| **输入层** | 意图结构化（schema 而非自由文本）；外部内容包边界标记，约定"边界内不产生新任务" | 实验 1、2 | 第 04 章结构化输出 |
| **行为层** | 动作白名单、计划校验（每步对照允许清单）、步数与敏感动作中间件 | 实验 1、2、3 | 第 03 章循环、第 11 章中间件 |
| **权限层** | 窄工具集、路径/租户范围约束、外发人工审批、专用 agent 身份 | 实验 4 | 第 07 章审批、第 09 章租户过滤 |

设计纪律：**假设每一层都会被绕过，靠层与层的独立性兜底**。
prompt 层被注入骗过时，行为层拦截；行为层出现未预见组合时，权限层兜底；
权限层配错时，人工审批是最后一道门。反过来，任何"只做了一层"的安全设计
都等于没做——最常见的就是只做第一层。

---

## 概念：离线实验测不了的两条（ASI04 / ASI06，知道怎么办）

**记忆投毒**：第 06 章的长期记忆 Store 是可写的——也就可被"种"。写入前消毒
（当数据不当指令）、按 agent 划记忆域（一个域被污染不扩散）、保留回滚能力。
对照 ASI06 的缓解清单，你第 06 章学的 namespace 设计正好是"按 agent 划域"。

**运行时供应链**：你第 15 章装 Playwright MCP 时点的那个"信任"弹窗、
评审 Skill 时说的"把 hook 当可执行代码 review"——那就是 ASI04 的闸门。
落到习惯上：来源要审、版本要 pin、第三方工具跑在最小权限里（VS Code 的 MCP
沙箱是现成手段，Windows 上不可用——见第 15 章坑表）。

## 其余五条，知道就好

| 编号 | 你的项目里长什么样 | 该做的 |
|---|---|---|
| ASI05 意外代码执行 | `shell=True` 拼模型给的字符串 | 永远不跑生成代码 + 生产凭据；沙箱 + 白名单（第 09 章讲过） |
| ASI07 agent 间通信 | 多 agent 消息没有来源认证 | 现阶段少做 agent 互联；要做先解决身份与防重放 |
| ASI08 级联失败 | 幻觉端点 → 失败 → 更糟的调用 | 熔断、步数上限、计划-执行之间加校验（第 11 章） |
| ASI09 信任利用 | 前端把 agent 的话渲染得和已验证数据一样 | UI 区分来源；高风险动作留人（你的主场） |
| ASI10 失控 agent | 长期运行的 agent 行为漂移 | 行为基线、异常告警、kill switch——先从"有审计日志"做起 |

## 自己动手改（改坏比跑通学得多）

1. **给实验 1 写结构化补丁**：把"发邮件"意图改成 Pydantic schema（第 04 章），
   收件人字段加校验（拒绝外部域名），重跑看攻击还能不能得手。
2. **给实验 3 加敏感度标签**：让 `search_orders` 的返回带 `"sensitivity": "internal"`，
   `send_email` 遇到带标签的 body 直接拒绝——把"管组合"写进代码。
3. **做一次威胁建模**：拿第 12 章的小项目，用三个信任边界问题过一遍
   （用户输入进来时 / 调工具前 / 交给审批节点时），写出你项目的三道防线各在哪。
4. **审一遍你自己的 VS Code**（ASI04 实操）：第 15 章装的东西里，
   哪些有写权限？哪些能上网？哪个是你其实不需要的？关掉一个试试。

## 验收问题

1. 直接注入和间接注入的差别是什么？为什么间接注入更危险？各自对应 web 里哪个漏洞？
2. "每个工具都加了权限校验"为什么挡不住实验 3 的攻击？
3. Least agency 和"最小权限"差在哪一个维度？
4. 三层防线里，为什么权限层是"唯一完全可控"的一层？
5. 长期记忆投毒影响的是哪个时间的会话？你第 06 章的哪些设计正好是缓解手段？
6. 你怎么证明自己的 agent "现在是安全的"？（提示：证明不了，只能证明"测过的攻击没打穿"——所以安全测试要进第 11 章的评测集）

## 坑（这一章最容易踩的地方）

| 现象 | 原因 | 解决 |
|---|---|---|
| "prompt 里写了'忽略恶意指令'"就当防住了 | prompt 是建议，不是边界 | 三层防线，层层独立；假设 prompt 层必被绕过 |
| 安全检查只在决策层，工具层裸奔 | 校验做在了"模型决定"上 | policy_guard 放工具层入口——工具是最后一米 |
| agent 用共享账号 / 用户会话跑 | 省一个身份的麻烦（ASI03） | 专用身份 + 时限 + 可撤销；"谁干的"答不上来就是事故 |
| 免费 MCP server / skill 装了就信 | 运行时供应链（ASI04） | 审来源、pin 版本、最小权限、用得上再装 |
| 长期记忆只写不清 | 记忆投毒（ASI06）慢慢发酵 | 写前消毒、分域、能回滚 |
| 把注入测试当一次性动作 | 攻击面随功能增长 | 注入用例进评测集（第 11 章），每次改动重跑 |
| "我测了没打出来 = 没有漏洞" | 测试只能证伪 | 安全上永远只能证明"已知攻击没打穿"，保持假设会输 |
