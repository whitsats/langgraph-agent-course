# 第 05 章：状态、reducer 与条件边

## 本章目标

1. 用 `StateGraph` 定义状态、节点、边，把流程从 prompt 里搬到图里
2. 彻底搞懂 **reducer**（这是 LangGraph 最容易出错、也最有价值的一层）
3. 用 `add_conditional_edges` 实现业务分流，并知道为什么它必须写在外面

**配套例子**：`examples/05_graph_basics.py`（**不需要 Key，现在就跑**）

---

## 概念：LangGraph 只有四个概念

| 概念 | 是什么 | 你的 Redux 类比 |
|---|---|---|
| **State** | 一个 `TypedDict`，全流程共享的数据 | store |
| **Node** | 一个函数：读 state，返回"这次的变化" | reducer / action handler |
| **Edge** | 节点之间的连线 | `dispatch` 的下一跳 |
| **Conditional edge** | 一个返回节点名的函数 | router / 中间件里的分支 |

`START` 是入口，`END` 是出口。`builder.compile()` 得到可执行的图，然后 `graph.invoke(初始状态)` 跑起来。

**为什么要用图，而不是写一堆 if-else？** 三个理由，都是工程理由：

1. **流程能被画出来**，也就能被人审查（你那个案例的分享稿讲的就是这个）
2. **每个节点能单独测试**，不必端到端跑一遍
3. **能挂 checkpointer**（第 06 章）——这是 if-else 永远做不到的：**流程能中断、能恢复、能回放**

---

## 概念：reducer（本章核心）

节点函数返回的不是"新状态"，而是**"这次的变化"**：

```python
def append_b(state: AppendState) -> dict:
    return {"items": ["b"]}      # 只返回要改的字段
```

那么问题来了：**"这次的变化"怎么并进已有状态？**答案就是 reducer。

```python
class A(TypedDict):
    items: list[str]                              # 没写 reducer

class B(TypedDict):
    items: Annotated[list[str], add]              # 写了 reducer（operator.add）
```

同一个节点、同一个返回值，结果完全不同：

```
没写 reducer      : ['b']         ← 'a' 被吃掉了
Annotated[..., add]: ['a', 'b']   ← 累加
```

一条规则记住：**不写 reducer 就是覆盖（overwrite）。**

**这是新手最常踩的坑**：你希望"多轮对话累积消息"，结果每轮只有最后一条——因为消息字段没挂 reducer。

### 想清空怎么办？

```python
g3: return {"items": []}              # ❌ 错误：空列表被"合并"进去，什么也没清掉
g4: return {"items": Overwrite([])}   # ✅ 正确：绕过 reducer，强制覆盖
```

**为什么？**因为累加型 reducer 看到 `[]` 的语义是"要追加一个空列表"。想真正清空，必须用 `Overwrite` **显式声明"忽略 reducer，直接覆盖"**。

### reducer 不只一个

| 场景 | 用什么 |
|---|---|
| 消息历史 | `Annotated[list, add_messages]`（LangGraph 预置，专门处理消息） |
| 普通列表累加 | `Annotated[list, add]` |
| 计数累加 | `Annotated[int, add]` |
| 自定义（去重、按 id 合并） | 自己写 `def merge(old, new) -> merged` |

## 跟着做

```bash
cd examples
uv run python 05_graph_basics.py
```

例子的第二部分是**订单审核**，故意用日常场景：

```python
def route_by_amount(state: OrderState) -> str:
    if state["amount"] <= 200:
        return "auto_approve"
    if state["amount"] <= 5000:
        return "manual_review"
    return "reject"

builder.add_conditional_edges("check", route_by_amount)   # ★ 分流在这里
```

跑出来是：

```
下单 88 元：     → 结论: approved (自动通过)
下单 1280 元：   → 结论: pending (等待人工)
下单 99999 元：  → 结论: rejected (超限)
```

**注意路由函数的位置**：它不在 prompt 里，不在节点里，而是**单独一个纯函数**。所以它可以被单元测试：

```python
assert route_by_amount({"amount": 100, ...}) == "auto_approve"
```

这是本章最该带走的设计原则：**业务规则和图结构，都不该靠模型自觉。**

## 看懂输出

```
没写 reducer      : ['b']   ← 'a' 被吃掉了
Annotated[..., add]: ['a', 'b']   ← 这才是我们要的
返回空 list       : ['a', 'b']   ← 空值被合并进去，根本没清掉
Overwrite([])     : []      ← 绕过 reducer，真正清空
```

四行输出，对应四种状态管理直觉。**把它们背下来比读十页文档有用。**

第二部分输出里，每个节点前都有 `[节点名]` 前缀：

```
  [check] 收到订单，金额 1280 元
  [manual_review] 中等金额，转人工复核
```

这个前缀是刻意加的——**它让你能画出流程的真实走向**。以后排查"流程为什么走了这条分支"，就是靠这种日志 + trace。

## 自己动手改

1. **把路由阈值改掉**（比如 200 → 1000），重跑，看结论变化。然后写一个断言测试它：`assert route_by_amount(...) == "manual_review"`。
2. **给 `manual_review` 加一个"再审核"环节**：加一个 `second_check` 节点，让 `manual_review → second_check → END`，观察多节点串联的写法。
3. **故意制造 reducer 错误**：把第二部分的状态里加一个 `log: Annotated[list[str], add]`，让每个节点都追加一行日志。**这是生产里很实用的技巧**（谁在什么时候做了什么，全在图里留痕）。
4. **把 `add_conditional_edges` 换成在节点里 `return {"decision": "..."}` 然后由外面判断**，对比一下：哪种更利于测试？哪种更容易写错？

## 验收问题

1. 节点返回值是"新状态"还是"这次的变化"？这个区别决定了什么？
2. 不写 reducer 会怎样？想清空带 reducer 的字段该怎么做，为什么？
3. 路由函数为什么必须是纯函数、必须返回值等于某个节点名？
4. 消息历史为什么用 `add_messages` 而不是 `add`？（提示：消息有 id）
5. `StateGraph` 的状态为什么只能用 `TypedDict` 而不能用 Pydantic 模型？

## 坑

- **忘了 reducer，越跑越丢数据**。特别是"多轮累积"的字段。
- **路由函数返回了一个不存在的节点名**。编译期不一定报错，运行时才炸，很隐蔽。
- **在节点里改全局变量当状态**。状态必须走 state，否则 checkpointer 存不到（第 06 章你会看到后果）。
- **在节点里写副作用**（发消息、扣款、写文件）：一旦有了中断和重跑（第 07 章），副作用会重复执行。**副作用应该放在最后一个节点，或者做成幂等**。
- **状态里塞大对象**：状态每次 checkpoint 都会落盘。塞数据库连接、大文件内容，会让存储爆炸（这种情况用 `UntrackedValue` 排除，第 06 章提）。
- **节点拆太细**：一个节点 = 一个决策。拆成十几个小函数，每次都要过一遍模型，又慢又贵。

## 想深挖

两个"知道就好"的能力，用到再回来查：

- **子图（subgraph）**：一张图可以当作另一个图里的节点——把大流程拆成可复用、可单独测试的小流程。
- **并行执行**：一个节点有多条出边时，目标节点会在**同一步里并行跑**（想串行就自己加中间节点）。阶段明确、要人工卡点的流程，往往用不上它。
