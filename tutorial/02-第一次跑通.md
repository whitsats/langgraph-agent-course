# 第 02 章：第一次跑通一个智能体

## 本章目标

1. 用不到 15 行跑通一个能干活的 agent
2. 学会看**消息轨迹**，而不是只看最后那句话
3. 打开 trace，从此"它到底看到了什么"不再是玄学

**配套例子**：`examples/05_hello_agent.py`

---

## 概念：`create_agent` 到底在替你做什么

一句话：**它实现了第 01 章说的那个循环**（调模型 → 执行工具 → 回灌 → 再调模型 → 直到不需要工具）。

```
create_agent(model, tools, system_prompt) 内部：
  1. 把 tools 转成模型能懂的 schema
  2. 调模型
  3. 有 tool_calls → 执行 → 打包成 ToolMessage 塞回消息列表 → 回到 2
  4. 没有 tool_calls → 返回整个消息列表
```

对你最重要的一层对应：**它返回的 `messages` 列表 = 这次会话的完整现场**。所以"最后那条消息"是答案，"列表里的每一条"才是过程。

> **旧写法警告**：你搜到的中文教程里如果出现 `AgentExecutor`、`initialize_agent`，那是 v0.x 的老 API，已经废弃。现在只有 `create_agent`（新）和 `langgraph.prebuilt.create_react_agent`（也已废弃，仅剩兼容）。

## 跟着做

```bash
cd examples
uv run python 05_hello_agent.py
```

代码的三个关键点（对着文件看）：

```python
agent = create_agent(
    model=get_model(),                    # ① 模型
    tools=[get_weather, calculate],       # ② 工具（就是普通函数 + @tool）
    system_prompt="你是一个简洁的助理。需要数据时必须调用工具，不要凭空猜。",   # ③ 行为约束
)

result = agent.invoke({"messages": [{"role": "user", "content": "上海天气怎么样？"}]})
print(result["messages"][-1].content)     # 输入是一个 dict，输出是一个 dict
```

注意三件事：

1. **输入输出都是 dict，键是 `messages`**。这是新版统一约定（不是 `input=`/`output=` 那一套）。
2. **`@tool` 装饰的 docstring 就是模型看到的工具说明**。写"查询指定城市的天气，city 是城市名"比写"查天气"准得多。
3. **`system_prompt` 里那句"不要凭空猜"是可以被验证的**——第 2 个问题就问它一个需要工具的问题，看它会不会老实调。

## 看懂输出

例子打完答案后会打印**消息轨迹**，这是本章的重点：

```
[0] HumanMessage   上海天气怎么样？
[1] AIMessage      [{'name': 'get_weather', 'args': {'city': '上海'}, 'id': 'call_xxx'}]
[2] ToolMessage    多云 26 度
[3] AIMessage      上海现在多云，26 度。
```

逐条读：

| 消息 | 谁产生的 | 你要看什么 |
|---|---|---|
| `HumanMessage` | 你 | 进模型的东西是不是你想的那样 |
| `AIMessage`（带 tool_calls） | 模型 | **它决定调哪个工具、参数是什么** |
| `ToolMessage` | 你的代码 | 工具真的返回了什么（不是模型说的） |
| `AIMessage`（纯文本） | 模型 | 最终答案 |

**判断一个 agent 好坏的关键在第 1 条和第 2 条之间**：

- 参数抽错了（`city` 抽成 `"上海天气"`）→ 是**工具描述**或**模型能力**的问题
- 该调不调 → 是 `system_prompt` 或模型的问题
- 工具返回了乱码/空 → 是你代码的问题

看轨迹能让你一眼定位到层。**只看最后那句话，你永远在猜。**

## 跟着做（第二部分）：打开 trace

```bash
# examples/.env 里加两行（去 smith.langchain.com 免费拿 Key）
LANGSMITH_TRACING=true
LANGSMITH_API_KEY=lsv2_...
```

再跑一次，控制台会打印一个链接。打开它，你会看到：

- 每一步的**完整输入**（包括被自动塞进去的 system prompt 和工具 schema）
- 每一步的 **token 数**和耗时
- 嵌套的调用链（模型 → 工具 → 再模型）

**为什么这一步要在第 2 天就做？** 因为智能体调试的 90% 时间花在"它到底看到了什么"。有了 trace，你不会再靠 `print` 猜；没 trace，你会把时间浪费在改 prompt 上。

## 自己动手改

1. **故意让它失败**：把 `calculate` 的工具描述改成 `"计算"`，再问一道计算题。看它还会不会调、参数抽得对不对。再把描述改回来对比。
2. **加约束**：把 `system_prompt` 改成 `"必须先调用工具再回答，否则视为错误"`，观察行为变化。**思考**：约束写在 prompt 里和写在代码里（比如直接调工具），可靠性差在哪？
3. **加一个你的工具**：写一个 `@tool def search_order(phone: str) -> str`，返回假数据，接进 `tools` 列表，问它"我的订单到哪了"。跑通后打印轨迹，看模型是怎么从"我的订单"里抽出手机号的。

## 验收问题

1. `agent.invoke(...)` 的返回结构里，为什么既有 `ToolMessage` 又有 `AIMessage`？
2. `@tool` 函数的 docstring 是谁在读？它影响什么？
3. 一个 agent "该调工具却没调"，你能从迹里定位到哪几种可能原因？
4. 为什么 trace 要尽早打开，而不是等出问题再打开？

---

## 坑

- **只看 `result["messages"][-1].content` 就下结论**。过程全在列表里，答案那句话骗人。
- **工具描述写得太短**。模型只能靠 docstring 和类型标注理解工具，写"查数据"等于没写。
- **以为 `system_prompt` 是硬约束**。它是强建议，不是权限控制。真正的硬约束要写在代码/工具层（第 11 章）。
- **忘了 `create_agent` 不支持 Pydantic 状态 schema**（只能用 `TypedDict`）——这是 v1 的明文限制，你到第 05 章会用到。
- **看到 `content` 是列表而不是字符串就慌**。某些模型会返回内容块（text / tool_use 等），打印时用 `str()` 包一层更稳。
