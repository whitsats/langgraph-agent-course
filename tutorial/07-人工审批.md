# 第 07 章：把人类放回流程

## 本章目标

1. 用 `interrupt()` 让流程停在中间，等人回答再继续
2. 记住那条**最容易出生产事故**的规则：恢复时节点会从头重跑
3. 分清"哪些事该交给模型、哪些事必须人拍板"，并把阈值写进代码而不是 prompt

**配套例子**：`examples/03_human_approval_offline.py`（离线）、`examples/10_hitl_graph.py`（需要 Key）

---

## 概念：中断不是"暂停程序"，是"存盘退出"

用你熟悉的话讲：**这不是 `sleep`，是"把现场序列化进数据库，然后浏览器/进程消失，等有人点按钮再加载回来"**。

```
invoke(...)  →  跑到 interrupt()  →  存下现场，返回 __interrupt__  →  （进程可以结束）
                                            ↓ 人回答
invoke(Command(resume=True), 同一 config)  →  从现场继续
```

**它为什么重要？** 因为真实业务里的审批不是"等几秒"，而是"等三天"。用 checkpointer 存现场，人第二天再来点同意，流程照样能续上——这在第 06 章的持久化基础上，是免费得到的。

## 跟着做

```bash
cd examples
uv run python 03_human_approval_offline.py
```

三段关键代码：

```python
# ① 停在这里，把问题抛给人
decision = interrupt({
    "问题": f"订单 {state['order_id']} 金额 {state['amount']} 元，是否批准？",
    "选项": ["同意", "拒绝"],
})

# ② 停下来之后怎么拿到待答内容（invoke 用法下看 __interrupt__）
result = graph.invoke(state_in, config)
interrupts = result.get("__interrupt__")

# ③ 恢复：resume 的值 = interrupt() 的返回值
final = graph.invoke(Command(resume=True), config)
```

**三个必备条件**，缺一个就跑不起来：

| 条件 | 为什么 |
|---|---|
| `compile(checkpointer=...)` | 没有存储，现场没地方放 |
| 同一个 `thread_id` | 恢复时要能找到那个现场 |
| `Command(resume=值)` | 这是"人给的答复" |

## 概念：那个致命的细节——节点会重跑

示例里这行注释是本章最重要的内容：

```python
def approve(state: OrderState) -> dict:
    # ⚠️ 这一行在【恢复时会再执行一次】。所以不要在这里写副作用（发消息、扣款、写文件）。
    print("  [approve] 进入审批节点（第一次会停在这里）")
    decision = interrupt({...})
```

**规则**：`interrupt()` 恢复时，**它所在的节点从函数开头重新执行**，然后 `interrupt()` 才返回你给的值。

所以：

```python
def approve(state):
    send_email("已提交审批")        # ❌ 人回答之后，这封邮件会再发一次
    decision = interrupt({...})
    charge_card(state["amount"])    # ❌ 更惨：可能重复扣款
```

**正确写法**（两种，选一种）：

```python
# A. 把副作用挪到 interrupt() 之后的独立节点（推荐）
def charge(state):     # 只有审批通过才会走到这里，且不会重跑
    ...

# B. 让副作用幂等（用 order_id 去重、加"已执行"标记字段）
def approve(state):
    if state.get("notified"):
        pass
    else:
        send_email(...); return {"notified": True}
```

**判断口诀：`interrupt()` 之前的代码，都要假定"会被执行很多次"。**

## 跟着做（模型起草 + 人工拍板）

```bash
uv run python 10_hitl_graph.py
```

这个例子把第 04 章的模型能力和本章的中断拼在一起，三个场景：

| 场景 | 金额 | 结果 |
|---|---|---|
| 小额退款 | 38 元 | 不中断，自动通过 |
| 大额退款 | 1280 元 | **中断**，人同意 → 受理 |
| 大额退款 | 2000 元 | **中断**，人拒绝 → 驳回 |

关键设计（值得抄进你的项目）：

```python
APPROVAL_THRESHOLD = 500          # ★ 业务规则写在代码里，不写在 prompt 里

def maybe_approve(state: RefundState) -> dict:
    if state["amount"] <= APPROVAL_THRESHOLD:
        return {"approved": True}          # 自动放行，不进 interrupt
    decision = interrupt({                 # 只有"该问人"的时候才问
        "问题": f"是否同意退款 {state['amount']} 元？",
        "诉求": state["request"],
        "模型草案": state["draft"],        # ★ 把模型起草的意见一起交给审批人
        "选项": ["同意", "拒绝"],
    })
    return {"approved": bool(decision)}
```

**注意到"模型草案"被塞进中断内容里了吗？**这是这套模式最漂亮的地方：**模型负责起草，人负责拍板，各做擅长的事**。审批人看到的不只是一个金额，还有一段可以直接用的回复草稿——审批从"看数字点同意"变成"审一份稿子"。

---

## 概念：审批不该只给"同意/拒绝"

`interrupt()` 的载荷是任意 JSON，所以你可以做出更细的审批交互：

| 模式 | 怎么做 | 适用 |
|---|---|---|
| 二元批准 | `resume=True/False` | 最简单，风险低 |
| 批准 / 编辑 / 拒绝 | `resume={"action": "edit", "text": "..."}` | **模型起草、人改稿**（最实用） |
| 补信息 | `resume={"补充": "..."}` | 模型缺参数时问人 |
| 多级审批 | 连续两个 `interrupt()`，或不同节点各一个 | 金额越高，层级越多 |

**注意**：`resume` 的值会原样变成 `interrupt()` 的返回值，所以复杂交互就是"传一个 dict 回来"，然后你自己解析。

## 自己动手改

1. **改阈值**：把 `APPROVAL_THRESHOLD` 改成 100，重跑，金额 38 那个场景也会中断。体会"同一套代码，业务规则一改就变"。
2. **制造重复副作用**：在 `approve` 里 `interrupt()` **之前**加一行 `print("已通知财务")`，然后观察输出——你会看到它打印了两次。**亲手看到一次，你就永远不会写错。**
3. **自定义 resume 值**：把 `Command(resume=True)` 改成 `Command(resume={"action": "edit", "text": "改成补偿 20 元优惠券"})`，然后在 `approve` 里解析这个 dict。做一个"批准但改稿"的流程。
4. **换成持久化**：把 `10_hitl_graph.py` 的 `InMemorySaver()` 换成 `SqliteSaver`，然后**分两次运行**：第一次跑到中断就退出，第二次用同一个 `thread_id` 恢复。这就是真实审批系统的形态。

## 坑

- **忘了 checkpointer**：`interrupt()` 会直接报错。
- **恢复时用了不同的 `thread_id`**：找不到现场，等于从头开始。
- **在 `interrupt()` 之前写副作用**：重复执行（发重复邮件、重复扣款的真凶）。
- **在 `invoke` 用法下找错地方**：待答内容在 `result["__interrupt__"]`；如果你用 `stream_events`，它在 `stream.interrupts` 上。两套 API 别混。
- **把审批做成"人在 prompt 里回复"**：那只是聊天，不是审批。**审批要拦住的是状态转移**（能不能进入下一个节点），不是某句话。
- **用同一个 `thread_id` 跑多个并发审批**：状态会互相污染。按业务实体（订单号）取 id。
