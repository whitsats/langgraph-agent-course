# 第 17 章：附录 D —— Agent 的规划与自我验证

> 第 03 章手写的循环是**一口气式**的：每一步都让模型重新看着全部对话现场发挥。
> 任务一大，这种 agent 就开始忘事、算错、硬编收尾。这一章给它两样东西：
> **先把计划写成对象**（能被校验、被执行、被修复），**再给每个结果配验收**
> （断言挡住"说成功其实失败"，验证器挡住"语气自信但编数字"）。
> 全程离线可复现——规划与验证的**结构**错了，换多强的模型都白搭。

**骨架**：LangChain 官方两篇规划文章（Plan-and-Execute Agents，2024-02-13；
Planning for Agents，2024-07-20）+ 三篇论文（Plan-and-Solve / ReWOO / Reflexion）。
**建议用时**：1 天。
**配套例子**：`examples/17_plan_and_verify_lab.py`（**离线可跑，不需要 Key**，已收编进 `run_all.py` 离线组）。

---

## 本章目标

1. 说清 plan-and-execute 比一口气式好在哪、**贵在哪**，什么时候值得用
2. 会给计划加**校验**、给执行加**断言**，失败只修那一步而不是从头再来
3. 会用 generator-verifier：让两个候选互相竞争，**外部验证器**裁决，而不是模型自己拍胸脯

---

## 跟着做

```bash
uv run python examples/17_plan_and_verify_lab.py
```

同一个咖啡店月报任务（查订单 → 查品类营收 → 落报告文件），四种做法逐步升级。
输出里的关键行：实验 1 的"月份数错 + 编造收尾"、实验 2 的三条 `❌ 拒绝`、
实验 3 的 `replanner：… 改为 2026-08` 和 `断点复用，跳过`、实验 4 的两行 `裁决`。

这些检查是**真断言**（`_shared.Checks`）：坏计划必须被拒、计划必须收敛、
断言过的步骤必须被复用、编造的候选必须被验证器挡下。任何一条失败，
脚本以非 0 退出码结束，`run_all.py` 会当场变红。

## 概念：一口气式 agent 的两个退化（为什么要规划）

第 03 章那种"模型每步重新看全部对话再拍板"的循环，任务一小很顺，
任务一大就开始退化。实验 1 复现了两个最典型的：

| 退化 | 实验 1 里的样子 | 根因 |
|---|---|---|
| **算错参数** | `revenue_by_category("2026-13")`——8 月被数成 13 月 | 每步都重新数一遍上下文，长上下文里数错很常见 |
| **编造收尾** | 工具明确报错，它答"最畅销品类是美式" | 错误信号被淹没，模型倾向给个"像样的答案"结束任务 |

**plan-and-execute** 的解法：把"想做什么"从循环里抽出来，先产出一份**计划**
（步骤清单），然后交给执行器逐步跑。官方博客给它的卖点是 faster / cheaper /
more performant——cheaper 的机制很直白：

| | 一口气式（ReAct 循环） | plan-and-execute |
|---|---|---|
| 决策调用 | **每步都要"模型"拍板** | 规划 1 次；执行零调用或小模型 |
| 上下文 | 每步塞全量对话历史 | 执行器只看当前步骤 |
| 出错后 | 原地打转或换个说法硬编 | 失败定位到步，只修那一步（实验 3） |

代价是**脆**：计划是提前写死的，执行中冒出新情况它不知道（所以需要重规划，
见下文）。什么时候值得用：**步骤能先想清楚、步骤数 ≥ 3、同样的任务反复跑**。
三步以内的一次性问答，一口气式更便宜——别为了模式而模式。

> 名词表（都是文献里的原名，见到不慌）：**Plan-and-Solve**（2023-05，先拆解再执行）、
> **ReWOO**（2023-05，规划时就写好变量占位符，工具结果一次填入——省 token 的极致版）、
> **LLMCompiler**（2023-06，把无依赖的步骤并行执行）。它们的差别只在"计划怎么写、
> 怎么执行"，骨架都是"计划是独立对象"。

## 概念：计划是对象——先校验，再执行（计划层断言）

实验 1 的做法 B 里，计划是一个**显式的数据结构**（`[("search_orders", "1001"), …]`）。
一旦它是对象，你就能在执行前做实验 2 的三件事：

1. **工具白名单**：计划里的每个工具都在允许集里吗？
2. **参数核对**：月份、订单号这类可枚举参数，在台账里存在吗？
3. **动作把关**：外发、写入这类高危动作，出现在这份计划里合理吗？

实验 2 的三个坏计划全部死在执行前：幻觉日期（`2026-13`）、幽灵工具
（`export_sales_csv`——**模型以为有这个工具**，第 04 章的坑又来了）、越权动作
（`send_email`）。这就是第 16 章 ASI08「计划-执行之间加校验」的落地；
而且第 16 章实验 3 那种"每步都合法、组合不合法"的外泄轨迹，
在计划层用工具白名单就能直接掐死——**比在执行层逐个放行安全得多**。

计划校验器和你写过的普通校验函数没有任何区别，三个检查加起来十几行。
Web 类比：计划校验是 **CI 里的 lint**——错误在 merge 前被拦，不是在生产上炸。

## 概念：执行断言 + 重规划——失败定位到步

计划再干净，执行还是会失败（台账更新了、网络抖了、参数就是错了）。
实验 3 是全章最实用的一段，两个动作：

**① 每步配验收断言。** 工具返回"成功"不等于做对了——这正是第 04 章
"工具失败必须显式"的延伸：不信任执行器的自述，**检查结果本身**。
例子里 `search_orders("1001")` 的断言是"输出里要有张三和 1280"。
没有断言的步骤等于白执行——你只是收集了一份没人验证过的输出。

**② 失败只修那一步。** 坏步骤被断言逼出**具体的错误**
（"2026-13 不在台账，可用月份：2026-07、2026-08"），replanner 拿着这份
错误修一步：`2026-13 → 2026-08`。对照一口气式：同样是"月份数错"，
一口气式把错误吞了然后编造收尾。

还有一行输出值得盯着：第 2 轮执行时，第 1 步显示 **"上轮已通过断言，断点复用，跳过"**。
已验证的步骤不重跑——这就是第 06 章 checkpointer 在真实系统里的价值：
**修复从断点重放，不从零开始**。生产里（LangGraph 官方 Functional API），
`@task` 的结果持久化后，重规划天然就是断点续跑。

## 概念：generator-verifier——候选竞争，外部裁决

前三个实验管"流程对不对"，实验 4 管"**答案对不对**"。做法：

1. 让生成器产出**多个候选**答案（提示词稍微不同，或干脆两个模型）
2. 用**外部验证器**逐条对账：候选里的每个可检验事实，都回台账核对
3. 采纳通过验证的候选；全都不通过，就把验证失败的原因喂回去重生成

实验 4 的两个候选：候选 1 语气自信（"遥遥领先"）但金额 9,000 是编的，
验证器对账时 `金额 9000：台账里查无此数 → 拒绝`；候选 2 语气朴素但每个数字
都对得上台账，采纳。**最终答案来自对得上台账的那个，不是最自信的那个。**

**为什么验证器必须在外部？** 让模型"自己检查自己"——同一个上下文、同一套
偏见，很容易顺着自己刚才的话再圆一遍。Reflexion 论文的自我批评是**文字**，
这里的对账是**断言**，后者硬得多。可用的外部验证器（按硬的程度排）：

| 验证器 | 硬度 | 例子 |
|---|---|---|
| 工具台账对账 | ★★★ | 金额、日期、状态码回数据库核对（实验 4） |
| 测试用例 | ★★★ | 生成的代码必须跑过测试（第 09 章沙箱 + 第 24 项） |
| 第二个模型（换提示） | ★★ | 换一套提示独立复核，避免同偏见 |
| 结构/schema 校验 | ★★ | Pydantic 过不过（第 04 章） |
| 模型自评 | ★ | 聊胜于无； Reflexion 的本意是拿环境反馈，不是自我陶醉 |

和第 16 章的连结：第 16 章的 **prompt 是建议，不是边界**；这一章同款结论是
**模型的自我评价是建议，不是验收**。安全靠代码层防线，正确性靠外部验证器。

## 概念：这些思想在官方体系里长什么样

LangChain 生态里你已经见过它们的名字，现在能对上号了：

| 出处 | 这一章的概念 | 一句话 |
|---|---|---|
| LangGraph **Functional API**（`@entrypoint` / `@task`） | 执行断言 + 断点复用 | 每个任务结果是持久化的——重规划 = 从断点重放已通过的步骤 |
| **Deep Agents** 的 `write_todos` 工具 | 计划是对象 | 官方 Harness 预制的规划工具：把待办清单写进状态、随做随勾 |
| **规划型 subagent / forked skill**（第 10、15 章） | 计划与执行分离 | 规划在主上下文，执行交给子上下文，互不污染 |
| 第 11 章**评测集**（矩阵第 35 项） | 验证器固化 | 任务级断言：调对工具、轨迹有界、终态正确——把实验 3 的断言搬到 CI |

**如果你只想记一件事**：计划不是装饰，它是能被**校验**（执行前）、被执行
（零决策调用）、被**修复**（失败只修那一步）的对象；验证不是文采，它是能被
**对账**的断言。

## 自己动手改（改坏比跑通学得多）

1. **给实验 2 加一条规则**：`write_report` 出现在计划里时，要求它的前两步
   必须是"查数据"类工具——把"先有数据再有报告"写成校验器代码。
2. **给实验 3 换一种失败**：把台账里 `2026-07` 的数据删掉再跑，观察
   replanner 的错误信息还够不够"可修复"——错误信息质量决定重规划质量。
3. **给实验 4 加"全都不过"分支**：两个候选都被拒绝时，把验证失败的原因
   拼回生成提示再生成一轮（这就是 Reflexion 的最小实现）。
4. **用真模型跑一次**：把实验 1 的 `one_shot_decide` 换成真模型调用
   （第 03 章写法），故意给 5 个以上步骤，观察它第几步开始算错月份——
   这就是"长任务必须规划"的实证。

## 坑（这一章最容易踩的地方）

| 现象 | 原因 | 解决 |
|---|---|---|
| 计划生成后直接执行，错一步废全部 | 计划没过校验就上线 | 执行前跑校验器：白名单 + 参数核对 + 动作把关 |
| 工具说成功就当成功 | 信任执行器自述 | 每步配断言，检查结果本身（第 04 章"显式失败"的延伸） |
| 失败后整个任务重跑 | 没有断点概念 | 已通过断言的步骤复用；生产里用 Functional API / checkpointer |
| 让模型"自己检查自己" | 同上下文同偏见，越检查越圆 | 外部验证器：台账 / 测试 / 换提示的第二模型 |
| 验证失败只说"不对" | 错误信息不可修复 | 验证器输出具体差异（"台账是 8420，候选说 9000"），喂回生成端 |
| 好任务也套 plan-and-execute | 为模式而模式 | 步骤能先想清楚、≥ 3 步、反复跑才值得；小任务一口气式更省 |
